# 评审报告：《计划-记忆整合插件.md》

## ① 主要问题/风险

### H1. 前提错误：工具名不冲突（严重度：高）

**位置**：决策1理由、问题1调研结论

**问题**：计划反复强调"Cordis 不支持覆盖已有工具注册"、"同名会抛出"，以此论证需要新建整合插件。但实际检查两个插件源码后发现：

- persona 注册：`memory`、`memory_search`
- auto 注册：`memory_log`、`memory_note`、`memory_user`、`memory_recall`、`memory_external` 等

**工具名完全不重叠**。计划基于错误前提推导出"需要整合插件"的结论。

### H2. 过度设计：用插件层解决配置问题（严重度：高）

**位置**：设计决策1、实现方式调研结论

**问题**：计划选择"新建独立插件 `dsh-memory-integrator`"，但实际只需要在现有 `cordis.patch.yml` 中添加配置覆盖：

```yaml
- id: persona-memory
  config:
    inject: false # 禁用注入
    learnEnabled: false # 禁用后台学习
```

从 persona 源码 `dist/index.js:183-232` 可见，`cfg.inject` 直接控制注入逻辑。cordis patch 的 config 覆盖机制已验证有效（当前 patch 中已有 `learnIntervalTurns: 3` 的先例）。

新建插件层：

- 增加维护负担（新包、新构建、新版本管理）
- 引入不必要的复杂度
- 没有解决任何配置层面无法解决的问题

### H3. 检索工具去重分析错误（严重度：中）

**位置**：决策4、表格"工具去重"

**问题**：计划称 `memory_recall` 和 `memory_search` 是"重复工具"，但实际上：

- `memory_recall`（auto）：关键词匹配 + 历史会话全文检索
- `memory_search`（persona）：FTS5 + 向量语义检索

两者功能互补，不是重复。计划自己也在决策4中说"两者功能互补，不重叠"，但标题却叫"检索工具去重"。

### H4. Pi 兼容性风险未充分评估（严重度：中）

**位置**：风险表、决策3

**问题**：计划提议屏蔽 persona 的 `memory` 工具，但：

- persona 的 `memory` 工具是与 Pi 共享 MEMORY.md 的核心接口
- 完全禁用会导致 DSH 侧无法通过 `memory` 工具读写共享记忆
- 风险表中只提到"与 Pi 共用记忆时注入格式变化"，未评估工具层面的影响

### H5. WebUI 面板依赖分析缺失（严重度：中）

**位置**：风险表、决策1

**问题**：计划声称"禁用原插件会破坏 WebUI 面板"，因此选择保留原插件。但实际上：

- persona 的记忆管理页是通过 `ctx.webServer.register()` 注册 API 路由
- 禁用 `inject` 和 `learnEnabled` 不会停掉 WebServer 路由
- 计划没有验证 WebUI 面板是否真的依赖注入逻辑

### H6. 验收标准不可量化（严重度：低）

**位置**：验收标准表

**问题**：

- "auto 的 autoStats.count 正常增长"——没有定义什么是"正常"
- "无 conflict 错误"——没有说明如何触发并发调用
- "两个原插件的面板仍可用"——没有定义验证方法

## ② 具体改进建议

### S1. 改为纯配置方案（响应 H1、H2）

**建议**：放弃新建整合插件，直接在 `cordis.patch.yml` 中添加：

```yaml
# 禁用 persona 的记忆注入和后台学习，保留其工具和 WebUI
- id: persona-memory
  config:
    inject: false # 禁止注入 <memory-context>
    learnEnabled: false # 禁止后台学习
    standingEnabled: false # 可选：禁止常驻指令注入
```

这样：

- 保留 persona 的 `memory` 和 `memory_search` 工具
- 保留 persona 的 WebUI 面板（API 路由不受配置影响）
- 禁用重复的注入和双跑的学习机制
- 零代码变更，零维护负担

### S2. 重新定义工具策略（响应 H3）

**建议**：

- 保留 `memory`（persona）和 `memory_user`/`memory_note`（auto）两个写入工具
- 保留 `memory_search`（persona，FTS5+向量）和 `memory_recall`（auto，关键词+会话）两个检索工具
- 明确分工：persona 负责 Pi 兼容和语义检索，auto 负责自动沉淀和日历

### S3. 补充 Pi 兼容性风险评估（响应 H4）

**建议**：

- 评估用户是否实际使用 Pi 共享记忆
- 如果不需要 Pi 兼容，可考虑完全卸载 persona 插件
- 如果需要，保留 persona 的 `memory` 工具，仅禁用注入和学习

### S4. 验证 WebUI 面板依赖（响应 H5）

**建议**：

- T1 调研任务中增加一项：检查 persona 的 WebUI 面板是否依赖 `cfg.inject`
- 如果面板只是展示 MEMORY.md 内容，不依赖注入逻辑，则可安全保留

### S5. 量化验收标准（响应 H6）

**建议**：

- 注入去重：检查 system prompt 中 `<memory-context>` 出现次数 = 0
- 工具可用性：调用 `ctx.tools.schemas()` 确认 `memory`、`memory_search`、`memory_recall` 存在
- 后台学习：检查日志中无 `[dsh-persona-memory] background learning` 输出
- 自动沉淀：确认 auto 的 `autoStats.count` 每轮增长

## ③ 整体可行性判断

**结论：不通过**

**理由**：计划基于错误前提（工具名冲突）推导出过度复杂的解决方案（新建插件层），而实际问题只需 3 行配置即可解决。当前方案增加维护负担且未验证 WebUI 依赖关系。建议改为纯配置方案，放弃整合插件开发。

> 一个 id-targeted patch 会替换对应条目的整个 `config`（未改字段也要重述）

```javascript
export function apply(ctx, config) {
    const cfg = {
        inject: true,
        learnEnabled: true,
        // ...
        ...config,  // cordis patch 的 config 会覆盖默认值
    };
```

从现有 `cordis.patch.yml` 中的先例：

```yaml
- id: persona-memory
  config:
    learnIntervalTurns: 3 # 已验证生效
```

### `ctx.tools.restrict` 限制

从 `packages/core/tools/README.md:22`：

> `ctx.tools.restrict(filter)` applies an agent-scoped allow/deny mask to global tools and **throws from a plain context**.

整合插件作为普通插件，无法使用 `restrict`。计划中"备选方案：注册一个'已禁用'的 memory 工具"也会因为重名抛出失败。
