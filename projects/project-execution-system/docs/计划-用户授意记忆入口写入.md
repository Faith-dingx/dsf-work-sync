## 一、背景与需求（用户原话引用）

用户提出以下最高权威需求：

1. **不给主 agent 乱改记忆文件的入口/工具**——主 agent 不得直接写记忆文件，不得新增任何"主 agent 写记忆"的模型工具
2. 添加**一个入口文件**（约定路径、单文件）
3. 记忆管理器**每次其他工作完成后扫描一次**该入口文件（不需要用户手动触发）
4. 扫描时**确认是「用户让主 agent 添加的」**（确认机制需设计权衡）
5. 确认后由**插件在合理的记忆文件里规范化添加**（三类内容映射：关键规则→MEMORY.md、用户偏好/档案→USER.md、项目→项目笔记 MEMORY.md、流水账→日志）
6. 未确认/格式不合规/超三类的内容**绝不写入**，标记并留待用户决策

### 现有实现约束（规划时必须对齐）

- 审核管线"不新增内容到记忆文件只校验"——本入口是**主动写入**，与审核管线的区别：入口文件是用户主动提交的内容，审核管线是对已写入内容的守门
- `WRITE_SOURCES` 枚举（`config.ts` L73-80）：`model-explicit/turn-stopping/persona-learning/history-compressor/unknown`——需新增 `'user-approved-entry'`
- `resolveWriteWaitMs()`（`config.ts` L83-94）：补 `'user-approved-entry'` 分支，建议 0ms（插件自写，无需等待）
- 已有 pendingWrite 注册/确认机制（`audit-pipeline/confirm.ts:39-65 PendingWriteRegistry` + `audit-pipeline/watcher.ts:90-133 MtimeWatcher`）+ mtime 轮询 watcher（5s）+ 六步管线
- 已有 `pending-suggestions.json`（历史甄别生成建议条目，`review-suggestions` CLI 确认后写入）
- 已有 `pending-review.json`（超三类内容标记，`archive.ts:57-109`）
- 注入管理器 SHORT_TERM_FILES 白名单——新入口文件不能误触发"超三类内容"标记
- 计划 v18 §4 文件存放映射表（MEMORY.md/USER.md/项目笔记/日志映射规则）
- guard-main-agent 文件策略（`docs/主agent可改写文件清单.yaml`）：**不修改主 agent 权限，入口文件路径不加入白名单即被拒绝**（`defaultPolicy: deny` fail-close 兜底，不新增 deny 规则类型）
- fail-open 红线不变：任何异常不自动写、不误写

## 二、方案设计（10 个设计点，全部明确）

### 2.1 入口文件路径与名称

**路径**：`<workspace>/.dsh-memory/user-entries.md`

**命名理由**：

- 放在 `.dsh-memory/` 根目录，与其他短期记忆文件（`pending-suggestions.json`、`conversationsummary-latest.md`）同一级，便于用户发现
- 文件名 `user-entries.md` 明确语义：这是用户主动提交的条目，非系统自动生成
- 不使用 `pending-` 前缀，以避免与 `pending-suggestions.json` 混淆——该文件需要用户主动写入内容，不是系统自动生成的待审队列
- 格式为 Markdown（而非 JSON），便于用户手写编辑，也便于阅读

### 2.2 三层安全防线（H-1 安全模型重构，核心）

**重要**：原 v1 依赖"主 agent 无法写"假设（`config.ts` 无 guard 拦截），主 agent 有通用 write 工具可伪造 `source=user` + 引用。**v2 改为三层防线组合，fail-close**。

#### 防线 1：guard 文件策略 fail-close（不加入白名单即拦截）

**落地方案（v2 终稿，实际实施口径）**：

- guard 文件策略（`docs/主agent可改写文件清单.yaml`）默认 `defaultPolicy: deny`（fail-close）：**不加入白名单即等于拒绝**——不需要、也不存在 deny 规则类型（`filePolicy.ts` `matchRule` 只有 `exact` / `prefix` 两种匹配，无 deny 规则）
- 入口文件 `<ws>/.dsh-memory/user-entries.md` **不在当前任何白名单 prefix 下**（当前白名单：`/home/dingx/DSF-work/docs/`、`/home/dingx/DSF-work/projects/*/docs/`、`/home/dingx/DSF-work/.temp/`、`/home/dingx/与agent的交互目录/`），所以主 agent 尝试写入必然被 deny——**零代码改动即拦截**
- 后续白名单扩展时，代码审查须核实此路径不被误纳入；guard-main-agent 源码/行为**零改动**，既有 115 测试保持全绿

**guard 防线说明**：主 agent 写 `user-entries.md` → guard `canWrite()` → 未命中任何 whitelist 规则 → `defaultPolicy: deny` → 返回 `kind: 'deny'` → 工具调用被拦截，主 agent 收到错误通知。

#### 防线 2：插件来源校验（格式守门）

入口文件格式 Schema（每个条目两行）：

```markdown
<!-- 用户授意条目 -->

[source=user] [target=memory|user|project|log] [project=<name>] <用户原话引用>

- <要写入的内容>
```

**格式校验规则**（`validators.ts` 新增 `parseUserEntryLine()` + `validateUserEntry()`）：

| 校验项           | 规则                                                   | 违规处理                                                      |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| source 字段      | 必须为 `user`                                          | 非 `user` → 不写入，静默跳过（非错误，不标记 pending-review） |
| target 字段      | 必须为 `memory/user/project/log` 之一                  | 非法 target → 标记 pending-review                             |
| project 字段     | target=project 时必须存在且非空                        | 缺 project → 标记 pending-review                              |
| **用户原话引用** | **必须包含 `用户说："..."` 或 `"..."` 格式的引号引用** | **无可识别引用 → 标记 pending-review（反伪造核心）**          |
| 内容行           | 必须以 `- ` 开头                                       | 格式不合规 → 标记 pending-review                              |

**反伪造断言（插件绝不写入的条件）**：

1. `source ≠ 'user'` → 静默跳过，不写目标文件，不写 pending-review（避免污染队列）
2. **无用户原话引用** → 标记 pending-review，不写目标文件
3. guard 拦截写操作 → 文件不存在/mtime 不变 → 插件不触发处理

#### 防线 3：用户显式确认时机（mtime 来源判定）

**方案**：利用 mtime 时间戳 + 操作来源区分。

插件在 poll 周期中检测到 `user-entries.md` 的 mtime 变化时，执行以下判定：

```
mtime 变化检测
    ↓
是插件自身写入导致的 mtime 变化？（registry.contains(filePath) 且 source='user-approved-entry'）
    → 是：跳过本次处理（防止循环）
    → 否：继续处理
    ↓
解析条目 → 校验 source/引用/target → 写入目标文件
```

**最简可落地的确认路径**（用户侧使用方式）：

1. 用户在本机 shell 编辑 `user-entries.md`（`echo >> user-entries.md` 或 `code` 编辑器）
2. 插件 poll（≤5s）检测到 mtime 变化
3. 插件解析条目 → 验证 source=user + 有引用 + target 合法
4. 写入目标文件 → 审计日志记录

**关键点**：mtime 变化来自用户 shell 编辑 → 插件识别为"用户主动提交"→ 自动处理；若主 agent 尝试写入（已被 guard 拦截，mtime 不会变化）→ 不会触发处理。

#### 反作弊断言总结（H-1 核心结论）

| 条件                        | 插件行为                                    |
| --------------------------- | ------------------------------------------- |
| source ≠ 'user'             | 静默跳过，不写目标文件，不写 pending-review |
| 无用户原话引用              | 标记 pending-review，不写目标文件           |
| guard 拦截写入              | mtime 不变化，插件不触发处理                |
| 权限异常（ENOTDIR 等）      | fail-open：跳过本轮，下一条 poll 重试       |
| 内容超三类（non-compliant） | 标记 pending-review，不写目标文件           |

### 2.6 与现有 pendingWrite/建议条目/审核管线的关系（S-5 pendingWrite skip-audit）

**与 pendingWrite 的关系**（S-5 关键改动）：

插件将条目写入目标文件时，**注册 pendingWrite（source=`user-approved-entry`）+ 标记 skip-audit**：

```typescript
// 写入目标文件前
registry.register(targetFile, 'user-approved-entry');
// 同时记录 skipAudit=true（防止审核管线对刚写入的目标文件重复触发 normalize/archive）
```

**审核管线识别 `user-approved-entry` 后的行为**：

- `resolveWriteWaitMs('user-approved-entry')` → **0ms**（插件自写，无需等待）
- 审核管线检测到目标文件变化 → consume → 识别为 `user-approved-entry` → **skip normalize/archive 两步**（跳过守门，因为内容已由插件层验证通过）→ 直接登记审计日志
- **`skip-audit` 在 confirm.ts/registry 的落地方式**：`PendingWriteRegistry` 新增 `skipAudit` 字段（可选，默认 false），`consume()` 返回 `{ source, skipAudit }`；`runAuditOnce()` 中 consume 后检查 `skipAudit`，若 true 则跳过 normalize/archive 直接标记 fixed

```typescript
// confirm.ts PendingWriteRegistry 新增
register(file: string, source: WriteSource, now = Date.now(), skipAudit = false): void {
  this.map.set(file, { source, timestamp: now, skipAudit })
}
consume(file: string, now = Date.now()): { source: WriteSource; skipAudit: boolean } | null {
  // ...
}

// index.ts runAuditOnce() 中
const pending = deps.registry.consume(file)
if (pending?.skipAudit) {
  fixed.push(file)  // 跳过 normalize/archive
  continue
}
```

**与普通审核管线的区别**：

- `user-approved-entry`（插件自写）→ skip-audit → 直接通过
- `history-compressor`（压缩器写）→ 正常走 normalize/archive（守门）
- 这样避免循环：插件写入目标 → 审核管线不会再次审核该目标

**与建议条目（pending-suggestions.json）的关系**：

两者独立，不共用同一机制：

- 建议条目：系统自动生成的待审条目，经 `review-suggestions` CLI 确认后写入
- 用户条目：用户主动提交的条目，经插件自动处理后写入（三层防线验证）

**SHORT_TERM_FILES 排除**：

- 入口文件**纳入** SHORT_TERM_FILES 监听（需要检测变化）
- 入口文件**不纳入** normalize/archive 两步（不修改入口文件本身）

### 2.7 处理完成后的状态更新

### 2.8 fail-open 与安全红线（v2 更新）

**安全红线**（任何异常不自动写、不误写）：

1. 入口文件读取失败 → 跳过本轮，不重试
2. 条目解析失败 → 标记 pending-review，不写入目标文件
3. 目标文件写入失败 → 记录审计日志，不破坏入口文件
4. 三类内容校验失败（non-compliant）→ 标记 pending-review，不写入目标文件
5. **guard 拦截主 agent 写入 → mtime 不变 → 插件不触发处理（防线 1 生效）**
6. **无用户原话引用 → 标记 pending-review（防线 2 生效）**
7. 所有异常均为 fail-open，不影响主流程和现有审核管线

**fail-open 链路**：

```
入口文件扫描失败 → 静默跳过（下一条 poll 再试）
条目验证失败 → 标记 pending-review，继续处理下一条
目标文件写入失败 → 审计日志记录，不回滚入口文件
guard 拦截写入 → mtime 不变，插件不触发
```

## 九、并发写入锁（M-8 明确）

**问题**：同一条 poll 周期中，多个条目写入同一目标文件（如两条 target=memory 条目）必须串行，避免写冲突。

**方案**：在 `user-entry-scanner.ts` 中实现 per-file 写入锁：

```typescript
// user-entry-scanner.ts
class FileWriterLock {
  private readonly queues = new Map<string, Promise<void>>();

  async withLock<T>(file: string, fn: () => Promise<T>): Promise<T> {
    const last = this.queues.get(file) ?? Promise.resolve();
    const next = last.then(fn, fn); // 前一个完成后执行当前写入
    this.queues.set(
      file,
      next.catch(() => {}),
    ); // 失败也释放锁
    return next;
  }
}
```

**落地方式**：`processUserEntries()` 中，按目标文件分组条目，每组串行执行写入；不同目标文件可并行处理。

## 十、部分失败策略（L-9 明确）

**原则**：每条条目独立处理，单条失败不影响其他条目。

**实现**：

- `processUserEntries()` 遍历条目时，每条条目独立 try/catch
- 单条失败 → 审计日志记录失败原因 → 继续处理下一条
- 部分成功状态：审计日志中记录 `success=N, failed=M`（如 `写入 3 条，失败 1 条`）
- pending-review 队列：单条失败不写入队列（失败条目不入队，等待下次 poll 重试）

```markdown
- 要写入的记忆内容
```

**注意事项**：

- 必须包含用户原话引用（`用户说："..."`），否则条目被标记 pending-review
- source 字段必须为 `user`，其他值被静默跳过
- target=project 时必须指定 project 名称
- 插件处理延迟 ≤5s（poll 间隔），无需手动触发

**查看待决条目**：

```bash
# 复用 review-suggestions CLI，指定 pending-review 类型
dsh memory review --type pending-review
```
