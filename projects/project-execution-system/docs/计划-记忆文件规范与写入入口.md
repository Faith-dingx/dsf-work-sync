7. 与审核管线衔接：归档写入也要过 pendingWrite 机制（或明确免审——管理器自身产物）
8. 验收标准量化：上下文长度控制、归档文件生成正确、无有价值信息丢失、fail-safe 设计

## 一、方案定位（v17 扩展）

### 1.1 管理器核心职责

**一个插件：`dsh-memory-manager`，模块化设计（审核管线 + 压缩模块）**

管理器的职责只有三条，不多不少：

| 职责                      | 说明                                                                                                                                                                               |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. 记忆文件维护**       | 校验/规范化/指针化，确保所有记忆文件符合用户三类内容规矩（①关键规则 ②关键文件指针 ③工作流水账指针）；超三类的内容→标记询问用户，不自动进入记忆文件                                 |
| **B. 每轮历史甄别与归档** | turn/end 后甄别历史内容类别（过时/无用/仍有用/有价值但非当前），按类别分别处理：过时/无用→归档到独立存档区；有价值但非当前→生成建议条目待审核确认后进记忆文件；仍有用→保留在上下文 |
| **C. 历史摘要注入**       | 基于甄别结果，生成摘要注入段（`dsh:conversation-summary`），仅承载"仍有用"的压缩结果，由注入管理器读取进上下文                                                                     |

**不是**：往记忆文件里直接新增内容（只生成建议→待审核确认）、不替代现有写入路径、不接管工作区文档（CHANGELOG/PROGRESS 等）、不自动丢弃有价值内容。

### 1.2 现有系统的边界

- **对话历史存储**：系统已有 `~/.dsh/sessions/<workspace>/session-*.jsonl.zstd` 存档，每会话独立，跨会话可检索（`tool-session-query`）。甄别归档**不另建存储体系**。
- **工作区文档**：CHANGELOG（改动明细）/ PROGRESS（进度）/ PROJECT（目标）/ projects/*/docs/进展.md 等，位置与归属不变，管理器不接管、不重写。
- **auto-memory 日志/反思**：已有 `memory_log` / `memory_reflect` 工具写入，管理器只做审核校验，不新增写入入口。

## 二、文件存放映射表（v17 更新：新增归档区）

| 内容                              | 存放位置                                                      | 规矩                                                   | 管理者是否接管  |
| --------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------ | --------------- |
| 每日日志                          | `.dsh-memory/*-MM-DD.md`（工作流水账指针）                    | 用户已定三类：一句项目内容 + 详细信息存项目文档        | ✅ 审核规范     |
| 记忆主文件                        | `~/.dsh/memory/MEMORY.md` / `USER.md`（关键规则/偏好/指针）   | 用户已定三类，零细节零无关                             | ✅ 审核规范     |
| 每日反思                          | `reflections/YYYY-MM-DD.md`（独立历史文档，按日一份）         | 用户已定：反思单独存放，不进其他文件                   | ✅ 审核规范     |
| 对话摘要                          | `.dsh-memory/conversationsummary-latest.md`（注入用）         | 单文件覆盖策略；只进注入段，不进记忆文件体系           | ✅ 审核规范     |
| 历史归档（过时/无用）             | `.dsh-memory/archive/history/<session-id>/<YYYY-MM-DD>.md`    | 归档可检索，不触发审核管线（不在 SHORT_TERM_FILES 中） | ❌ 不归审核管线 |
| 归档建议条目                      | `.dsh-memory/pending-suggestions.json`                        | 待审核确认后才写入目标记忆文件                         | ✅ 审核规范     |
| 审计/待决临时产物                 | `.dsh-memory/` 内（审核管线中间状态、pending-review.json 等） | 管理器内部使用，定期清理归档                           | ✅ 管理器内部   |
| CHANGELOG / PROGRESS / PROJECT 等 | 工作区 `docs/` / `projects/*/docs/`                           | 用户已定，位置归属不变                                 | ❌ 不归管理器   |

**关键原则**：管理器的审核管线只管"符合规矩的文件内容是否被规范地维护"，不管"应该放什么内容"。内容体系由用户约定决定，管理器是守门员，不是创作者。**归档区（archive/history/）不在审核管线监听范围内**，避免循环触发。

## 三、短期记忆文件内容规范（核心）

> （§3.1~3.5 与 v16 相同，不变）

### 3.6 对话历史摘要（conversationsummary-latest.md）—— v17 更新：只承载"仍有用"部分

**定位**：每轮甄别+压缩后的产物，临时性上下文优化，**不进记忆文件体系**，仅作为注入段（`dsh:conversation-summary`）进入当轮 context。**只包含经分类判定为"仍有用"的内容**，不含过时/无用/有价值但非当前的内容。

#### 结构规范

```markdown
# 对话历史摘要

> 生成时间：2026-08-22 10:30  
> 覆盖范围：第 3-8 轮（保留最近 2 轮原文）  
> 压缩策略：基于内容甄别的结构化摘要（已过时/无用内容已归档）

## Primary Request

- 第 3 轮：用户要求修复 guard 误拦问题
- 第 4 轮：分析 timeoutMs 配置不足

## Key Concepts

- 9888 软路由网关
- classifier timeout 配置
- fail-close 安全策略

## Files

- packages/extensions/guard-main-agent/src/classifier.ts
- ~/.dsh/.agent-presets/full/agent.cordis.yml

## Errors

- timeoutMs=5000 不足（9888 延迟 6.5s）
- caller abort 未正确处理

## Pending Jobs

- guard 修复方案评审
- preset 配置更新
```

#### 内容规范

| 维度         | 规范                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **允许内容** | 仅"仍有用"类别的历史片段精华摘要 + 关键概念/文件/错误 + 待办事项                                                            |
| **禁止内容** | ①过时/无用内容 ②完整对话原文（保留最近 N 轮）③无关寒暄 ④临时测试                                                            |
| **来源标注** | 必须含生成时间、覆盖范围、压缩策略说明（含"已过时/无用内容已归档"标识）                                                     |
| **长度预算** | 总行数 ≤ 50行；单节 ≤ 10 条                                                                                                 |
| **生命周期** | 当轮 context 内有效，跨 session 自然失效                                                                                    |
| **文件策略** | **单文件覆盖**：每次压缩写入同一文件 `.dsh-memory/conversationsummary-latest.md`，无需带时间戳；定期维护清理过期摘要（7天） |

#### 校验规则

```javascript
{
  mustHave: ['Primary Request', 'Key Concepts', 'Files', 'Errors', 'Pending Jobs'],
  mustNotHave: ['full_conversation', 'chitchat', 'stale_content', 'useless_content'],
  maxLines: 50,
  maxSections: 5
}
```

> **注意**：单文件策略与 §3.2.4 两处一致；定期维护见 §5.3。

### 3.7 历史归档文件格式（v17 新增）

**定位**：过时/无用内容的落盘存档，按会话+日期组织，**可检索但不在审核管线范围内**。

#### 文件路径规范

```
.dsh-memory/archive/history/<session-id>/<YYYY-MM-DD>.md
```

示例：`.dsh-memory/archive/history/abc123/2026-08-22.md`

#### 文件结构

```markdown
# 归档历史：2026-08-22

> 会话：abc123  
> 归档时间：2026-08-22 10:30  
> 归档原因：内容过时/对当前任务无用  
> 来源轮次：第 3-8 轮（已压缩）

## 过时内容

- 临时路径 `/tmp/test-xxx`（已清理，见 CHANGELOG.md）
- 已完成子任务"guard 修复"的原始讨论（已完成，见 CHANGELOG.md）
- 过期配置 `timeoutMs=5000`（已改为 10000）

## 无用内容

- 闲聊："今天天气不错"
- 已放弃的探索方向：方案 A（因性能问题弃用，见 `projects/xxx/进展.md`）
- 错误尝试：直接用硬编码路径（已改用环境变量）

## 有价值但非当前（已生成建议条目）

- 跨任务规则：用户偏好"工作完成后立即记录" → 见 `pending-suggestions.json`
- 项目指针：`docs/计划-guard-main-agent.md` 可作为模板参考
```

#### 归档规范

| 维度           | 规范                                                   |
| -------------- | ------------------------------------------------------ |
| **按会话隔离** | 每个 session-id 独立目录，不混入其他会话内容           |
| **按日期命名** | 文件名含日期，便于时序检索                             |
| **内容标注**   | 每条归档内容标注来源轮次和归档原因                     |
| **指针引用**   | 如有相关项目文档，标注指针路径                         |
| **可检索性**   | 保留完整原文（不删减），确保未来可通过归档检索工具恢复 |

## 四、插件模块化设计（核心）

### 4.1 插件整体架构

**一个插件，模块化文件结构**：

```
dsh-memory-manager（线2）
├── 模块 A：audit-pipeline（记忆文件审核管线）
│   ├── ① 发现写入（mtime 轮询）
│   ├── ② 确认写入完毕（写入源识别）
│   ├── ③ 与之前版本对比（diff 计算）
│   ├── ④ 按三类规矩校验+规范化（非"整理内容"）
│   ├── ⑤ 归档修改（格式自动修正 / 超三类内容标记询问）
│   └── ⑥ 记录审计日志
│
└── 模块 B：history-compressor（历史对话甄别+归档+压缩）
    ├── 触发：turn/end 事件
    ├── 动作①：内容分类（classify）—— LLM 判定每段历史的类别
    ├── 动作②：归档处理（archive）—— 按类别分别处理
    │   ├── 过时/无用 → 归档到独立存档区
    │   ├── 有价值但非当前 → 生成建议条目（pendingWrite 注册）
    │   └── 仍有用 → 保留原文或进摘要
    ├── 动作③：摘要生成（summarize）—— 基于甄别结果生成摘要
    ├── 输出：conversationsummary-latest.md（单文件覆盖，只进审核管线 + 注入段）
    └── 进入：审核管线（步骤①）
```

**模块化文件结构**：

```
packages/extensions/dsh-memory-manager/
├── src/
│   ├── index.ts                 # 插件入口：组装两个 listener，编排时序（先甄别归档→后摘要→再审核）
│   ├── config.ts                # 插件配置项（阈值、轮询间隔、模型、归档路径等）
│   │
│   ├── audit-pipeline/          # 【模块A】记忆文件审核管线
│   │   ├── watcher.ts           # ① mtime 轮询检测 + 变化发现

│   │   ├── normalize.ts         # ④ 按三类规矩校验+规范化（校验超限只精简不删，语义问题标记询问）

│   │   ├── classify.ts          # ① 内容分类：LLM 轻量判定每段历史类别（过时/无用/仍有用/有价值但非当前）
│   │   ├── archive.ts           # ② 归档处理：按类别分别写入（归档区/建议条目/保留）
│   │   ├── summarize.ts         # ③ LLM 摘要生成（自实现，走插件 config 配置模型，基于甄别结果）

│   │   └── inject.ts            # dsh:conversation-summary 注入协同（配置导出）
│   │
│   └── shared/                  # 【模块C】共享工具
│       ├── validators.ts        # 各文件类型规范校验器
│       └── logger.ts            # 审计日志工具
│
├── tests/
│   ├── audit-pipeline.spec.ts   # 审核管线模块测试（watcher/confirm/diff/normalize/archive）

│
```

**模块职责边界**：

- `audit-pipeline/`：纯粹的文件审核逻辑，按三类规矩校验，不新增内容
- `history-compressor/`：
  - `classify.ts`：纯粹的 LLM 分类逻辑，输出结构化类别标签
  - `archive.ts`：纯粹的归档逻辑，按类别分别处理（写归档区/写建议条目/保留原文）
  - `summarize.ts`：纯粹的摘要生成逻辑，基于甄别结果生成"仍有用"部分的摘要
  - `write-summary.ts` / `write-archive.ts`：写入协同，注册 pendingWrite
- `shared/`：纯工具函数，无副作用
- `index.ts`：插件入口，负责监听事件并编排时序（先甄别归档→后摘要→再审核）

### 4.2 职责面 B：历史对话每轮甄别+归档+压缩模块（v17 扩展）

#### 4.2.1 触发时机

**事件**：`turn/end`（每轮对话结束后）

**时序**：

```
turn/end 事件
    ↓
① 历史对话甄别+归档+压缩（history-compressor 模块，v17 扩展）
    ├── ①.1 内容分类（classify）—— LLM 判定每段历史类别
    ├── ①.2 归档处理（archive）—— 按类别分别处理
    │   ├── 过时/无用 → 归档到独立存档区
    │   ├── 有价值但非当前 → 生成建议条目（pendingWrite 注册）
    │   └── 仍有用 → 保留原文或进摘要
    └── ①.3 摘要生成（summarize）—— 基于甄别结果生成"仍有用"部分摘要
    ↓
② 记忆文件审核（audit-pipeline 模块，六步管线）
    ↓
下一轮 assemble 前
```

**理由**：

- turn/end 是会话生命周期最合适的处理点：一轮完成、上下文稳定、下一轮开始前
- auto-memory 已在 turn-stopping 时写入日志（`memory_log` 等），甄别归档在其后执行，语义清晰
- 与现有 compaction 的 `agent/pre-step` 触发点互补：pre-step 是压力驱动，turn/end 是主动维护
- 不影响运行时性能：turn/end 时 agent 已空闲
- **并发安全**：auto-memory 写日志文件与压缩模块写归档/摘要文件是不同文件，无冲突；审核管线多文件时队列串行处理（fail-open 兜底）

#### 4.2.2 内容甄别与分类规则（v17 新增）

**→ 选择：LLM 轻量分类 + 规则兜底**

**分类维度**：每段历史内容判定为以下四类之一：

| 类别               | 定义                                                                         | 处理路径                                                                  |
| ------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **过时**           | 已完成的子任务、已被后文替代的决策、过期临时信息（如临时路径、一次性 token） | 归档到独立存档区（`.dsh-memory/archive/history/`），从注入上下文移除      |
| **无用**           | 无关闲聊、前期探索（已放弃方向）、错误尝试（已修正）、与当前任务无关的信息   | 归档到独立存档区，从注入上下文移除                                        |
| **仍有用**         | 当前任务需要的事实/结论/依赖、正在进行中的决策、关键文件路径                 | 保留在上下文（近轮原文或进摘要注入段）                                    |
| **有价值但非当前** | 跨任务有价值的内容（如通用规则、可复用模式、重要项目指针）、但当前任务不需要 | 按三类规矩生成建议条目 → 待用户/审核确认 → 写入相应记忆文件（不自动直写） |

**判定主体**：

- **主要**：LLM（agnes-2.5-flash）轻量分类——每轮压缩时调用，输入历史片段 + 当前任务上下文，输出类别标签
- **当前任务上下文来源**：从 `assembly.contexts` 读取（注入管理器输出的当轮 assembly 内容），包含：
  - 近期 user message（最近 3 轮）
  - 当前 pending jobs（从摘要或 MEMORY.md 提取）
  - 关键文件路径引用
- **跨轮一致性处理**：相同历史片段在多轮分类中结果应一致；若 LLM 输出置信度 < 0.6，标记为"待复核"而非随机降级，确保同类内容分类稳定
- **兜底规则**：满足以下任一条件时直接归类，不经 LLM：
  | 规则类型   | 条件                                             | 类别 |
  | ---------- | ------------------------------------------------ | ---- |
  | 时间阈值   | 内容 mtime > 7 天 且 无后续轮次引用              | 过时 |
  | 寒暄检测   | 内容仅包含"你好/谢谢/再见/天气不错"等寒暄关键词  | 无用 |
  | 已完成标记 | 内容含"[已完成]/[done]/✅"等标记且无后续相关轮次 | 过时 |
  | 临时信息   | 内容含"/tmp/"、"临时路径"、"一次性"等关键词      | 无用 |
  | 重复内容   | 内容与近 3 轮已有内容完全相同                    | 无用 |
- **置信度机制**：LLM 输出附带置信度分数，低于阈值（如 < 0.6）时降级到规则判定或标记待人工复核

**输入输出规范**：

```typescript
// classify.ts 接口
interface HistorySegment {
  turnId: string;
  content: string;
  timestamp: Date;
  isUser: boolean;
}

interface ClassifiedResult {
  segmentId: string;
  category: 'stale' | 'useless' | 'useful' | 'valuable-but-not-current';
  confidence: number; // 0-1
  reasoning?: string; // LLM 判定理由（可选，用于审计）
}

async function classifySegments(
  segments: HistorySegment[],
  currentTaskContext: string,
  config: PluginConfig,
): Promise<ClassifiedResult[]>;
```

**为什么用 LLM + 规则混合**：

- LLM 能理解语义上下文，准确判断"过时"vs"有价值但非当前"
- 规则兜底避免 LLM 误判（尤其是高置信度场景）
- 成本可控：只调用便宜模型（agnes-2.5-flash），且仅在阈值触发时执行

#### 4.2.7 与 compaction-basic 的关系（v17 更新）

**→ 选择：叠加，fail-open 链**

| 维度     | 现有 compaction-basic     | 本轮甄别+归档+压缩（v17）                    |
| -------- | ------------------------- | -------------------------------------------- |
| 触发     | 压力阈值 / overflow       | 每轮 turn/end                                |
| 执行位置 | surface log（持久化）     | context 注入 + 归档写入                      |
| 压缩范围 | 从头到 retention boundary | 只压缩超出 N 轮的历史                        |
| 目的     | 防止上下文超限            | 每轮保持轻量上下文 + 提前归档过时/无用内容   |
| 优先级   | 兜底安全网                | 日常维护                                     |
| 额外价值 | 无                        | 归档有价值但非当前内容到记忆文件（建议模式） |

**fail-open 链设计**：

- 本插件压缩成功 → 降低上下文基数，compaction-basic 不触发或延迟触发
- **本插件压缩失败**（classify/summarize/archive 任意模块异常）→ fail-open，compaction-basic 正常触发作为兜底
- 两者互不冲突，各自独立运作

**验证要求**：

- T16 验收需包含：模拟本插件压缩失败场景，验证 compaction-basic 仍能正常触发压力兜底

## 五、写入处理六步管线设计（v17 修正语义）

### 5.1 管线流程总览

```
① 发现写入     —— 检测到短期记忆文件被修改（mtime 轮询/watch）
    ↓
② 确认写入完毕 —— 确认写入完成（文件稳定、结合上端动作来源确认写入源）
    ↓
③ 与之前版本对比 —— diff 当前版本 vs 上次审核过的版本，明确"改了什么"
    ↓
④ 按三类规矩校验+规范化 —— 对照该文件的内容规矩检查新增/修改内容：
                         超三类内容 → 标记询问用户（不自动进记忆）
                         格式不规范 → 自动规范化
                         超长 → 精简不删除
    ↓
⑤ 归档修改       —— 格式自动修正 / 超三类内容标记等待用户决策
    ↓
⑥ 记录审计日志   —— 所有操作留痕
```

**v17 语义修正**：步骤④⑤的核心是"按三类规矩校验"（守门），不是"整理/修改内容"（创作）。管理器不新增任何内容到记忆文件，只确保已有内容符合规矩。**归档区（archive/history/）不在审核管线范围内，不触发循环**。

### 5.2 各步骤详细说明

#### 步骤①：发现写入

**触发机制**：

- **推荐方案**：mtime 轮询（每 5 秒扫描一次，由 `watcher.ts` 模块实现）
- **备选方案**：`fs.watch()` 文件系统监听（实时但开销稍高）

**监听文件列表**（v17 更新：不含归档区）：

```javascript

  '~/.dsh/memory/USER.md',
  '.dsh-memory/*-MM-DD.md', // 日志

  '~/.dsh/memory/CALENDAR.md',
  '.dsh-memory/conversationsummary-latest.md', // 对话摘要（单文件）
  '.dsh-memory/pending-suggestions.json', // 建议条目（单文件）
  // 注意：.dsh-memory/archive/history/ 不在监听范围内，避免循环触发
];
```

**检测逻辑**：

```javascript
async function detectWrite(filePath) {
  const stat = await fs.stat(filePath);
  if (stat.mtime > lastSeenMtime[filePath]) {
    lastSeenMtime[filePath] = stat.mtime;
    return { detected: true, filePath, mtime: stat.mtime };
  }
  return { detected: false };
}
```

#### 步骤②：确认写入完毕

**目的**：防止读到半截写入的内容，同时识别写入来源以便确定等待策略

**写入源分类（WRITE_SOURCES）**：

| 写入源               | 来源                                 | 等待策略                 | 说明                         |
| -------------------- | ------------------------------------ | ------------------------ | ---------------------------- |
| `model-explicit`     | memory_write 工具调用                | 无需等待（已知原子操作） | 插件直接落盘，内容已完整     |
| `turn-stopping`      | auto-memory turn-stopping 回调       | 缩短等待（≤500ms）       | 单次 appendText 调用，速度快 |
| `persona-learning`   | persona-memory runLearning/store.add | 缩短等待（≤500ms）       | 同上                         |
| `history-compressor` | 本插件甄别归档模块                   | 缩短等待（≤500ms）       | 插件内部调用，速度快         |
| `unknown`            | 无法匹配上游事件                     | 保持2秒兜底              | 降级策略                     |

**写入源识别机制（含 pendingWrite 注册）**：

为解决"compressor 写摘要/建议条目时轮询器如何识别写入源"问题，采用 **pendingWrite 内存 map 机制**：

1. **写前注册**：`history-compressor/write-summary.ts` 和 `write-archive.ts` 在写文件前，向 `confirm.ts` 注册的 `pendingWrite` map 写入 `{filePath, source, timestamp}`
2. **轮询检测**：`audit-pipeline/watcher.ts` 检测到 mtime 变化后，`confirm.ts` 先查 `pendingWrite` map：
   - **命中**：确认写入源，采用缩短等待（≤500ms）
   - **未命中**：降级到 Cordis 事件匹配（turn-stopping/persona-learning），再未命中则 `unknown`
3. **写后清除**：写入完成后清除对应 map 条目（超时 5s 自动清理）

```javascript
// confirm.ts 中的 pendingWrite map
const pendingWrites = new Map<string, {source: string, timestamp: number}>();

// write-summary.ts / write-archive.ts 写前注册
pendingWrites.set(filePath, {source: 'history-compressor', timestamp: Date.now()});

// confirm.ts 检测
function detectWriteSource(filePath) {
  const pending = pendingWrites.get(filePath);
  if (pending && Date.now() - pending.timestamp < 5000) {
    pendingWrites.delete(filePath); // 消费后清除
    return pending.source;
  }
  // 未命中 → 走 Cordis 事件匹配
  return detectByEvent(filePath);
}
```

**实现路径**：

- 监听 Cordis 事件（`agent/turn-stopping` 等）记录 `{sessionId, agentId, timestamp}`
- mtime 变化时查最近事件匹配 source
- 无匹配时降级 `unknown`

**检测策略**：

```javascript
async function confirmWriteComplete(filePath, maxWaitMs = 2000) {
  const startTime = Date.now();
  let lastSize = -1;

  while (Date.now() - startTime < maxWaitMs) {
    const stat = await fs.stat(filePath);

    // 策略1：文件大小稳定（两次读取相同）
    if (stat.size === lastSize) {
      return { complete: true, size: stat.size, source: detectWriteSource(filePath) };
    }

    lastSize = stat.size;
    await sleep(100); // 100ms 间隔检查
  }

  // 超时：认为写入完成，继续处理
  return { complete: true, timeout: true, size: lastSize, source: 'unknown' };
}

function detectWriteSource(filePath) {
  // 1. 先查 pendingWrite map（history-compressor 写前注册）
  const pending = pendingWrites.get(filePath);
  if (pending && Date.now() - pending.timestamp < 5000) {
    pendingWrites.delete(filePath);
    return 'history-compressor';
  }
  // 2. 再查 Cordis 事件匹配
  return detectByCordisEvent(filePath);
}
```

**步骤②输出结构**：

```json
{
  "complete": true,
  "size": 1234,
  "source": "history-compressor",
  "timeout": false
}
```

**状态可序列化**：上述结构可直接存储，支持断点续处理。

#### 步骤④：按三类规矩校验+规范化（v17 修正）

### 5.3 定期维护机制

**触发方式**：

- **每日定时任务**：每天凌晨 2:00 执行（不影响用户使用）
- **手动触发**：用户通过命令 `dsh memory maintain` 触发

**维护范围**：全部短期记忆文件（含对话摘要、建议条目）；**不含归档区**

**维护动作**：

| 动作               | 说明                                                                                                                    | 执行条件     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------- | ------------ |
| **完整巡检**       | 对所有文件做一次规范检查                                                                                                | 每次执行     |
| **过时内容识别**   | 扫描标记为 `[临时]`/`[待定]`/`[等待]` 的条目，超过 N 天未更新则标记"疑似过时"，纳入待处理队列询问用户                   | 每次执行     |
| **历史压缩**       | 压缩超过 7 天的日志条目                                                                                                 | 发现冗长条目 |
| **重复清理**       | 合并跨日重复条目                                                                                                        | 发现重复     |
| **摘要清理**       | 清理超过 7 天的对话摘要（单文件策略：定期维护时若 latest 文件超过 7 天未更新则归档到 `.dsh-memory/archive/summaries/`） | 每次执行     |
| **建议条目清理**   | 清理超过 7 天未处理的建设条目（自动删除或标记过期）                                                                     | 每次执行     |
| **待处理队列检查** | 通知用户处理待确认问题（含建议条目确认）                                                                                | 队列非空     |
| **审计日志归档**   | 归档超过 30 天的日志                                                                                                    | 每次执行     |
| **归档压缩**       | 90 天以上归档文件进行 gzip 压缩存储，命名规则：`<YYYY-MM-DD>.md.gz`（如 `2026-08-22.md.gz`）                            | 每次执行     |
| **归档区整理**     | 超过 90 天的历史归档文件从 `.md` 压缩为 `.md.gz`                                                                        | 每次执行     |

**维护流程**：

```javascript
async function scheduledMaintenance() {
  // 1. 扫描所有短期记忆文件（含摘要、建议条目）
  const files = await scanShortTermFiles();

  // 2. 对每个文件执行完整巡检
  for (const file of files) {
    await fullAudit(file);
  }

  // 3. 过时内容识别：扫描 [临时]/[待定]/[等待] 标记
  const staleItems = await identifyStaleContent(files);
  if (staleItems.length > 0) {
    await addToPendingReview(staleItems);
  }

  // 4. 清理过期摘要（单文件策略：latest 超过 7 天则归档）
  await cleanupOldSummaries();

  // 5. 清理过期建议条目
  await cleanupExpiredSuggestions();

  // 6. 检查待处理队列
  const pending = await getPendingQuestions();
  if (pending.length > 0) {
    await notifyUser(pending);
  }

  // 7. 归档旧日志
  await archiveOldAuditLogs();

  // 8. 整理归档区（90 天以上压缩存储）
  await consolidateHistoryArchives();
}
```

### 5.4 与现有插件的关系

**边界声明**：

```
现有插件（auto/persona）          记忆与上下文管理器（本插件）
        ↓                                ↓
     后台直写文件（不拦截）       六步处理管线 + 历史甄别归档
        ↓                                ↓
       写入完成                 ① 发现写入（轮询）
                                ② 确认写入完毕（识别写入源：pendingWrite map + Cordis 事件）
                                ③ 与之前版本对比
                                ④ 按三类规矩校验+规范化（守门，不创作）
                                ⑤ 归档修改（格式自动 / 超三类标记询问）
                                ⑥ 记录审计日志
                                ↓
                          定期维护（每日巡检 + 过时内容识别 + 摘要清理 + 建议条目清理）
```

**写路径分类表**（v17 更新）：

| 写路径           | 来源                                 | 是否经过 memory_write | 处理方式                                 |
| ---------------- | ------------------------------------ | --------------------- | ---------------------------------------- |
| 模型显式写入     | 模型调用 memory_write 工具           | 是                    | 六步管线完整处理（按三类规矩校验）       |
| auto 后台沉淀    | auto-memory turn-stopping 回调       | 否                    | 轮询发现 → 审计 + 规范检查               |
| persona 后台学习 | persona-memory runLearning/store.add | 否                    | 轮询发现 → 审计 + 规范检查               |
| 历史摘要         | 本插件 compression 模块              | 否（内部调用）        | 写前注册 pendingWrite → 直接触发审核管线 |
| 历史归档         | 本插件 archive 模块                  | 否（内部调用）        | 不触发审核管线（归档区不在监听范围）     |
| 建议条目         | 本插件 classify 模块                 | 否（内部调用）        | 写前注册 pendingWrite → 触发审核管线校验 |

**关键原则**：

- 不修改现有插件代码
- 不拦截写入路径
- 只在写入后处理
- fail-open：插件异常不影响现有功能
- **摘要段名 `dsh:conversation-summary` 加入 SHORT_TERM_MEMORY_NAMES 白名单是必要协同（非禁用注入管理器）**
- **管理器只维护规矩，不新增内容体系**
- **归档区不在审核管线范围内，避免循环触发**
