## 二、需求：工具按需配给

### 2.1 设计决策

#### 决策 1a：放现有注入管理器扩展 vs 单独处理

**→ 选择：扩展现有 dsh-injection-manager**

**理由：**

1. 注入管理器已在 `system-prompt/assemble` 层持有 `assembly.tools`，是工具裁剪的唯一正确位置
2. 现有静态裁剪（5 读留、10 写裁）和动态裁剪是同一问题的不同阶段——先静态基础裁剪，再动态按需增删
3. 独立插件会导致两个工具裁剪逻辑并行，增加维护负担和不一致风险
4. 其他 agent（code-agent 等）的静态 preset 已固定，不需要动态能力；只有 full preset 需要此能力

#### 决策 1b：静态精简 vs 动态按需

**→ 选择：先静态精简（立即省 token），再叠加动态按需（按需激活 browser/vision）**

**理由：**

- 之前否决的是"按任务类型动态裁剪记忆工具"，原因是主 agent 只读不需写——**不适用于 browser/vision**（这两组工具与主 agent 核心职责无关，但确实偶尔需要）
- 用户说"按需配给"，倾向动态，但**静态基线裁剪是前提**：先把确定不用的工具从 full preset 移出，再对剩余的大体积工具（browser 24 + vision 15）做动态管理
- 两步走策略：T1-T3 做静态基线，T4-T6 做动态按需

#### 决策 1c：动态触发机制

**→ 选择：复用 skill-router classifier 的判断，注入管理器在执行时调用**

**流程：**

```
turn 开始
  ↓
skill-router classifier 判断当前任务是否需要 browser/vision
  ↓
返回结构：{ needsBrowser: boolean, needsVision: boolean }
  ↓
注入管理器读取分类结果，动态 add/remove browser/vision 工具组
  ↓
最终 assembly.tools = 全量注册 → 静态裁剪（memory 10写）→ 动态裁剪（按需 browser/vision）
  ↓
fallback：classifier 失败时 fail-open（保留全部工具）
```

**关键设计：**

- skill-router 已有 `classifierEndpoint` + `classifierModel` 配置（preset 里已有），可直接复用它做意图分类
- 分类 prompt 需新增"任务是否需要浏览器操作/视觉分析"的判断
- 注入管理器在 `assemble` 阶段读取 classifier 结果，动态 add/remove browser/vision 工具组
- **fail-open**：classifier 失败或超时 → 保留所有工具（不丢功能）
- **classifier 降级阈值**：连续 3 次失败时启用 fail-open，避免持续误判

#### 决策 1d：主 Agent 固定基线工具集

**→ 建议从 full preset 移出的工具（归入"按需池"）：**

| 工具组       | 数量   | Token 估算 | 移出原因                    |
| ------------ | ------ | ---------- | --------------------------- |
| browser 全部 | 24     | ~4.5K      | 主 agent 极少直接操作浏览器 |
| vision 全部  | 15     | ~1.5K      | 主 agent 极少直接分析图片   |
| **合计**     | **39** | **~6K**    | **省约 24% 工具空间**       |

**主 Agent 固定基线（保留）：**

- core：read/write/edit/glob/grep/str_replace_editor/...（~8 个）
- subagent：subagent/fork/list-agents/...（~4 个）
- search：web_search/advanced_search/platform_search/...（~4 个）
- session：session_event_read/search/trace（~5 个）
- memory（只读）：memory_read/recall/search/status/calendar_list（~5 个）
- cordis：tool-cordis（~1 个）
- agent-infra：tool-todo/ask-user/web/goal/jobs/fs-search/terminal/bash-persistent/lsp/skill（~10 个）
- guard-main-agent / skill-router（已注册服务，非工具）
- **总计：~36 个固定工具（从 97 → 36，省约 63% 工具定义 token）**

> ⚠️ 实际精确数量需在 T1 测量后确认。此处为估算。

### 2.2 两段裁剪叠加顺序

**静态裁剪先，动态裁剪后，两者均 fail-open：**

```
全量注册 tools（97个）
  ↓
【静态裁剪】注入管理器 tool-cut 10写（107→97）
  ↓
【动态裁剪】按 classifier 结果 add browser/vision 组
  ↓
最终 assembly.tools（36-75个，视任务需要）
```

**关键规则：**

1. **顺序固定**：静态裁剪先执行（确保 memory 10写工具始终隐藏），动态裁剪后执行（按需激活 browser/vision）
2. **fail-open**：静态裁剪或动态裁剪任一环节异常，都不影响下游工具可用性
3. **guard 无需同步**：被动态裁剪掉的工具模型看不到就不会调用，自洽；动态 add 后 guard 按 preset 配置自动生效
4. **恢复路径**：需要 browser/vision 时，classifier 返回 true → 注入管理器 add 回工具组

---

### 2.3 方案详述：两阶段实现

**阶段 A：静态基线裁剪（T1-T2）**

1. 从 full preset `agent.cordis.yml` 移除 browser/vision 工具注册行
2. 验证：full preset 工具数从 97 → ~58，token 注入量下降
3. 验证：不影响其他 preset（code-agent/check-agent 等不受影响）

**阶段 B：动态按需池（T3-T6）**

1. 注入管理器新增 `dynamic-tool-groups` 配置 + `dynamic-tool-cut.ts`
2. 新增 config 项 `DYNAMIC_TOOL_GROUPS`（声明 browser/vision 工具组可动态裁）
3. skill-router 分类 prompt 扩展：新增"是否需要 browser/vision"判断分支
4. 注入管理器 assemble 钩子读取 classifier 结果，动态 add/remove 工具组
5. fail-open fallback：classifier 连续 3 次失败时启用 fail-open

## 五、风险项

| 风险                            | 严重度 | 缓解措施                                                                                                             |
| ------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------- |
| **动态裁剪误裁工具**            | 中     | fail-open 策略（classifier 失败时保留全部）；连续 3 次失败启用降级；先做静态裁剪（T1-T3），动态按需作为叠加（T4-T6） |
| **主 Agent 能力受损**           | 高     | 静态基线先做（T1-T3），验证子 Agent 不受影响后再做动态（T4-T6）；动态裁剪可配置 threshold 逐步放开                   |
| **skill-router 分类准确率不足** | 中     | 分类 prompt 需充分测试（≥20 样本）；fallback 确保 fail-open；可渐进式引入（先默认隐藏，分类准确后再启用）            |
| **注入管理器复杂度增加**        | 中     | 分 T4/T6 独立模块，保持单一职责；每个模块有独立测试                                                                  |
| **工具裁剪后 guard 边界**       | 低     | 被动态裁剪掉的工具模型看不到就不会调用，自洽；动态 add 后 guard 按 preset 配置自动生效，无需额外同步                 |
| **主 Agent 重启后需用户操作**   | 低     | 已有约定：主 Agent 不做重启，改完配置后告知用户重启                                                                  |

## 七、特别思考

### 7.1 "按需配给"与静态裁剪的边界

用户说"按需配给"，严格含义是工具**按需出现在上下文**。这与现有注入管理器的"静态固定裁剪"是不同维度：

- **静态裁剪**：哪些工具永远不在这个 preset 里（从 preset yaml 移除）
- **按需配给**：哪些工具默认不在，但任务需要时可激活

本计划采用**先静态后动态**策略：

- 静态：browser/vision 工具从 full preset 移除（省 token）
- 动态：注入管理器按 skill-router 分类结果动态 add 回来（按需激活）

这样既满足用户"按需配给"的意图，又保证静态基线已足够精简。

### 7.2 廉价模型中转的用户约束

主 Agent 用 agnes-2.5-flash（免费），工具/历史设计要贴合省钱目标：

- 减少工具定义 token → 减少每轮输入 token → 直接省钱
- 压缩用免费模型（agnes-2.5-flash via router-9888）→ 压缩本身也省钱

预期收益：

- 静态裁剪后：单轮注入从 ~25.1K → ~19K（省 ~6K，约 24%）
- 动态按需时：按任务需要增减，平均约 18-20K token
