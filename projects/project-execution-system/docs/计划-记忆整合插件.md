# 计划-记忆整合插件

## 背景与问题

本机 `~/.dsh/profiles/web` 同时运行两个记忆插件：

- `dsh-persona-memory` 0.2.0（bundle: `dsh-persona-memory`）
- `@a9i5k4/dsh-auto-memory` 0.1.28（bundle: `@a9i5k4/dsh-auto-memory`）

两类插件产生四类冲突：

| 冲突               | 表现                                                                                                    | 证据位置                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| MEMORY.md 双读双写 | persona 的 `memory` 工具与 auto 的 `memory_user` 都读写 `~/.dsh/memory/MEMORY.md`；每轮注入两次相同内容 | persona: `dist/lib/prompt.js:4-25`（`renderMemoryBlock`）；auto: `lib/index.js:745`（`part('用户级记忆...'）` |
| 检索/读取工具重复  | persona: `memory`/`memory_search`；auto: `memory_read`/`memory_recall`/`memory_external`                | persona: `dist/index.js:145-146`；auto: `lib/index.js:2708-3336`                                              |
| 自动写入双跑       | persona 每 10 轮后台学习提取事实；auto 每轮自动沉淀 + 30 天蒸馏                                         | persona: `dist/lib/learning.js:34-103`；auto: `lib/index.js:2645-2661`（`turn-stopping`）                     |
| 纪律注入叠加       | 两套 memory 纪律都注入 system prompt，模型需同时遵守                                                    | persona: `dist/index.js:220-231`；auto: `lib/index.js:782-800`                                                |

---

## 设计决策

### 决策 1：整合方式 —— 新建整合插件统一管理

**选择**：新建独立插件 `dsh-memory-integrator`，接管工具注册 + 注入，**不直接修改现有两个插件代码**。

**理由**：

- Cordis 插件系统不支持"覆盖"已有工具注册（源码：`packages/core/tools/README.md:20` — "Duplicate names within one layer throw"）
- 禁用原插件会破坏其 WebUI 面板（persona 的"记忆管理"设置页、auto 的"记忆"侧边栏面板）
- 整合插件作为新 bundle 层，可精确控制工具集和注入内容

**依据**：

- DSH 工具注册：同层同名会抛出（`ctx.tools.register` 文档）
- Cordis patch 机制：支持 `insert`/`config override`，但不支持"工具名覆盖"
- 现有 plugins 均通过 `cordis.patch.yml` 的 `insert` 块注入

---

### 决策 2：主导方选择 —— 以 auto 为主、persona 为辅

**选择**：保留 auto 的核心功能（日志/反思/沉淀/日历），引入 persona 的向量检索能力（`memory_search` 的 FTS5 + 向量混合检索）。

**理由**：

| 能力         | auto 优势                   | persona 优势                    |
| ------------ | --------------------------- | ------------------------------- |
| 自动沉淀     | ✅ 每轮自动、GUI 面板丰富   | ❌ 仅后台学习（10 轮/次）       |
| 日历管理     | ✅ 完整四象限 + AI 主动维护 | ❌ 无                           |
| 每日反思     | ✅ 结构化反思 + 自动检测    | ❌ 无                           |
| 外部记忆继承 | ✅ WorkBuddy/Codex 等接入   | ❌ 无                           |
| 向量检索     | ❌ 仅关键词                 | ✅ FTS5 + 语义向量 RRF 融合     |
| Pi 兼容      | ❌ DSH 独有格式             | ✅ 与 pi-hermes-memory 字节兼容 |

**整合策略**：

- 继承 auto 的三层记忆结构（用户级/项目笔记/每日日志）
- 引入 persona 的 `memory_search` 工具（FTS5 + 向量）作为增强
- 屏蔽 persona 的 `memory` 工具（避免双写）

---

### 决策 3：MEMORY.md 写入权 —— 归 auto，persona 的 `memory` 工具屏蔽

**选择**：

- `memory_user` / `memory_note` 保留（auto 的工具）
- `memory` 工具（persona）**屏蔽**：注册一个 no-op 版本或完全不注册
- `memory_search` 工具（persona）**保留**：作为检索增强

**理由**：

- auto 有卫生闸门（`sanitizeForWrite`）、每日预算、自动压缩，更安全
- persona 的 `memory` 工具无预算控制，容易超限
- 两个插件都读写 `MEMORY.md`，必须去重

**实现方式**：

- 整合插件不注册 persona 的 `memory` 工具
- 在 `cordis.patch.yml` 中用 `disable: true` 禁用 persona 的 `memory` 工具注册（需验证 cordis 是否支持此功能）
- 备选方案：注册一个"已禁用"的 `memory` 工具，返回"请使用 memory_user/memory_note"

---

### 决策 4：检索工具去重 —— 保留 auto 的 `memory_recall` + persona 的 `memory_search`

**选择**：

- 保留 `memory_recall`（auto）：覆盖会话全文 + 外部记忆
- 保留 `memory_search`（persona）：覆盖 FTS5 + 向量语义检索
- 两者功能互补，不重叠

**理由**：

| 工具                | 覆盖范围                                                          | 优先级                    |
| ------------------- | ----------------------------------------------------------------- | ------------------------- |
| `memory_recall`     | 本地记忆（关键词）+ 历史会话全文 + 外部记忆（WorkBuddy/Codex 等） | 主检索入口                |
| `memory_search`     | MEMORY.md 的 FTS5 全文 + 向量语义检索                             | 增强检索                  |
| `memory`（persona） | 读写 MEMORY.md                                                    | ❌ 屏蔽                   |
| `memory_read`       | 读取特定文件                                                      | ❌ 合并到 `memory_recall` |

**包装方案**（可选）：

- 整合插件可提供统一入口 `memory_integrated`，内部路由到 `memory_recall` 或 `memory_search`
- 但不推荐：增加复杂度，不如保持两套清晰

---

### 决策 5：注入去重 —— 禁用 persona 的 `<memory-context>` 段，保留 auto 的 `[用户级记忆]` 段

**选择**：

- **禁用** persona 的 `inject` 配置（`config.inject = false`）
- **保留** auto 的 `injectEnabled: true`

**理由**：

- persona 的注入格式（`<memory-context>` + `### MEMORY` + `### USER`）较简陋，无预算控制
- auto 的注入格式（`<memory_system>`）更丰富，含纪律、语体要求、时间戳
- auto 的注入位于 system prompt 末尾（order: 10000），优先级更高

**实现方式**：

```yaml
# cordis.patch.yml
- id: persona-memory
  config:
    inject: false # 禁用 persona 的记忆注入
```

---

### 决策 6：自动写入双跑 —— 停掉 persona 的后台学习，保留 auto 的每轮沉淀

**选择**：

- **禁用** persona 的后台学习（`config.learnEnabled = false`）
- **保留** auto 的每轮自动沉淀（`autoConsolidate: true`）

**理由**：

- persona 的后台学习每 10 轮触发一次，调用 LLM 提取事实，风格与 auto 不一致
- auto 的沉淀机制更完善：有每日预算、自动压缩、卫生闸门、GUI 反馈
- 两者都写 MEMORY.md，会导致重复写入

**实现方式**：

```yaml
# cordis.patch.yml
- id: persona-memory
  config:
    inject: false
    learnEnabled: false # 禁用后台学习
```

## 实现方式调研结论

### 问题 1：能否通过 cordis.patch.yml 的 disable 禁用某个插件的行？

**结论**：**可以部分禁用，但不能禁用单个工具**。

依据：

- Cordis patch 机制支持 `config` 覆盖（`packages/extensions/tool-cordis/README.zh.md`）
- persona-memory 的 `inject` 配置可控制注入行为（`dist/index.js:149`）
- persona-memory 的 `learnEnabled` 配置可控制后台学习（`dist/lib/learning.js:86`）
- 但无法通过 patch 禁用单个工具注册（`ctx.tools.register` 在插件代码内）

**可行方案**：

```yaml
- id: persona-memory
  config:
    inject: false # 禁用注入
    learnEnabled: false # 禁用后台学习
    standingEnabled: false # 禁用常驻指令（可选）
```

### 问题 2：能否在整合插件 apply 时用 ctx 拦截/覆盖已有工具？

**结论**：**不能覆盖，但可以 restrict 屏蔽**。

依据：

- `ctx.tools.register`：同层同名会抛出（`packages/core/tools/README.md:20`）
- `ctx.tools.restrict(filter)`：可以 agent-scoped 地屏蔽全局工具（`packages/core/tools/README.md:22`）
- 但 `restrict` 需要 agent context，插件层可能无法直接使用

**可行方案**：

- 整合插件注册时检查工具是否存在，若存在则跳过（不抛出）
- 或使用 `ctx.tools.guard()` 拦截对特定工具的调用

### 问题 3：DSH 是否有"工具名去重/覆盖"机制？

**结论**：**没有原生覆盖机制，同层同名会抛出**。

依据：

- `ctx.tools.register` 文档明确："Duplicate names within one layer throw"
- 工具注册是"先注册先得"，后注册的同名工具会失败
- 没有 `registerOrReplace` 或 `registerOverride` API

**可行方案**：

- 整合插件只注册不冲突的工具（`memory_search`）
- 冲突的工具（`memory`）由 persona 自己不注册，或整合插件不做处理（让它失败）

## 扩展位设计

### 未来"另搞自动系统"的扩展位

整合插件预留以下扩展点：

1. **统一工具入口**：`memory_integrated` 工具，内部路由到 `memory_recall` 或 `memory_search`
2. **配置中心化**：所有记忆配置统一通过整合插件的 `cordis.patch.yml` 管理
3. **插件链机制**：支持未来新增记忆插件时，自动去重和冲突检测

### 降级/Fail-safe

- 整合插件加载失败时，两个原插件**各自独立工作**（无整合效果，但无破坏）
- 用户可通过删除 bundles 中的 `dsh-memory-integrator` 回退到双插件模式
- 整合插件不修改原插件代码，可随时卸载
