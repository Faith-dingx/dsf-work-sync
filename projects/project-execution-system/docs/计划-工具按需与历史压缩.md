## 二、需求 1：工具按需配给

### 2.1 设计决策

#### 决策 1a：放现有注入管理器 vs 单独处理

**→ 选择：扩展现有 dsh-injection-manager**

**理由：**

1. 注入管理器已在 `system-prompt/assemble` 层持有 `assembly.tools`，是工具裁剪的唯一正确位置（工具在 assemble 后、请求前决定）
2. 现有静态裁剪（5 读留、10 写裁）和动态裁剪是同一问题的不同阶段——先静态基础裁剪，再动态按需增删
3. 独立插件会导致两个工具裁剪逻辑并行，增加维护负担和不一致风险
4. 其他 agent（code-agent 等）的静态 preset 已固定，不需要动态能力；只有 full preset 需要此能力

#### 决策 1b：静态精简 vs 动态按需

**→ 选择：先静态精简（立即省 token），再叠加动态按需（按需激活 browser/vision）**

**理由：**

- 之前否决的是"按任务类型动态裁剪记忆工具"，原因是主 agent 只读不需写——**不适用于 browser/vision**（这两组工具与主 agent 核心职责（编排/调度）无关，但确实偶尔需要）
- 用户说"按需配给"，倾向动态，但**静态基线裁剪是前提**：先把确定不用的工具从 full preset 移出，再对剩余的大体积工具（browser 24 + vision 15）做动态管理
- 两步走策略：T1-T3 做静态基线，T4-T6 做动态按需

#### 决策 1c：动态触发机制

**→ 选择：复用 skill-router classifier 的判断，注入管理器在执行时调用**

**流程：**

```
turn 开始
  ↓
skill-router 判断当前任务是否需要 browser/vision
  ↓
结果注入 assembly.tools（通过注入管理器的 system-prompt/assemble 钩子）
  ↓
fallback：classifier 失败时 fail-open（保留全部工具）
```

**关键设计：**

- skill-router 已有 `classifierEndpoint` + `classifierModel` 配置（preset 里已有），可直接复用它做意图分类
- 分类 prompt 需新增"任务是否需要浏览器操作/视觉分析"的判断
- 注入管理器在 `assemble` 阶段读取 classifier 结果，动态 add/remove browser/vision 工具组
- **fail-open**：classifier 失败或超时 → 保留所有工具（不丢功能）
- **与静态裁剪的顺序**：静态裁剪（memory 10 工具）→ 动态按需（browser/vision 按需增删）→ 最终 tools 列表

#### 决策 1d：主 Agent 固定基线工具集

**→ 建议从 full preset 移出的工具（归入"按需池"）：**

| 工具组       | 数量   | Token 估算 | 移出原因                    |
| ------------ | ------ | ---------- | --------------------------- |
| browser 全部 | 24     | ~4.5K      | 主 agent 极少直接操作浏览器 |
| vision 全部  | 15     | ~1.5K      | 主 agent 极少直接分析图片   |
| **合计**     | **39** | **~6K**    | **省约 24% 工具空间**       |

**主 Agent 固定基线（保留）：**

- core：read/write/edit/glob/grep/str_replace_editor/...（~8 个）
- subagent：subagent/fork/list-agents/...（~4 个）
- search：web_search/advanced_search/platform_search/...（~4 个）
- session：session_event_read/search/trace（~5 个）
- memory（只读）：memory_read/recall/search/status/calendar_list（~5 个）
- cordis：tool-cordis（~1 个）
- agent-infra：tool-todo/ask-user/web/goal/jobs/fs-search/terminal/bash-persistent/lsp/skill（~10 个）
- guard-main-agent / skill-router（已注册服务，非工具）
- **总计：~58 个固定工具（从 97 → 58，省约 40% 工具定义 token）**

> ⚠️ 实际精确数量需在 T1 测量后确认。此处为估算。

## 三、需求 2：历史对话每轮即时整理压缩

### 3.1 设计决策

#### 决策 2a：触发时机

**→ 选择：`turn/end` 事件后立即执行（与 auto-memory 沉淀同点）**

**理由：**

- `turn/end` 是会话生命周期最合适的压缩点：一轮完成、上下文稳定、下一轮开始前
- auto-memory 已在 turn-stopping 时写入日志（`memory_log` 等），压缩在其后执行，语义清晰
- 与现有 compaction 的 `agent/pre-step` 触发点互补：pre-step 是压力驱动，turn/end 是主动维护
- 不影响运行时性能：turn/end 时 agent 已空闲

#### 决策 2b：压缩策略

**→ 选择：轻量摘要压缩（非完整 compaction）——早期轮次 → 结构化摘要，保留近期原文**

**策略详述：**

- 只压缩**超过 N 轮之前**的历史（如保留最近 5 轮原文 + 早期轮次摘要）
- 摘要格式：复用 compaction-basic 已有的 `<compacted-summary>` 结构（Primary Request / Key Concepts / Files / Errors / Pending Jobs）
- 摘要内容**不**进入持久化 session log，只进入当轮 system prompt 的 memory 注入段（作为"对话精华摘要"上下文）
- 压缩产物存入 `dsh:conversation-summary` context（新注入名，纳入 SHORT_TERM_MEMORY_NAMES）

**为什么不完全复用现有 compaction：**

- 现有 compaction 是"替换 surface nodes"（持久化到 session log），代价高、涉及 durable mutation
- 每轮都做完整 compaction 会引入不必要的开销和复杂度
- 轻量摘要方案：只把早期轮次的精华注入到下一轮的 context 里，**不改 session log**，风险更低

#### 决策 2c：与现有 compaction-basic 的关系

**→ 选择：叠加，不替代**

| 维度     | 现有 compaction-basic     | 本轮压缩（新）                 |
| -------- | ------------------------- | ------------------------------ |
| 触发     | 压力阈值 / overflow       | 每轮 turn/end                  |
| 执行位置 | surface log（持久化）     | context 注入（临时，不进 log） |
| 压缩范围 | 从头到 retention boundary | 只压缩超出 N 轮的历史          |
| 目的     | 防止上下文超限            | 每轮保持轻量上下文             |
| 优先级   | 兜底安全网                | 日常维护                       |

两者互不冲突：

- 轻量压缩每天/每轮执行，降低整体上下文基数
- 压力 compaction 作为兜底，当累积仍然超标时强制触发

#### 决策 2d：执行载体

**→ 选择：扩展 dsh-injection-manager（新增 `turn-end-compact` 模块）**

**理由：**

1. 注入管理器已在 system-prompt/assemble 层，有上下文组装权限
2. 可复用 compaction-basic 的 summarizer 逻辑（`summarizeWithLlm`）
3. 统一管理：工具裁剪 + 历史压缩在同插件，配置集中
4. compaction-basic 插件负责持久化 compaction（兜底），注入管理器负责每轮轻量维护（主动）

**具体实现路径：**

- 在 `dsh-injection-manager` 中新增 `turn-end-compact.ts`
- 监听 `turn/end` 事件，检查历史轮次数是否超过阈值
- 若超过，调用 summarizer 对早期轮次生成摘要，注入到 `dsh:conversation-summary` context
- 此 context 在下一轮 `system-prompt/assemble` 时由注入管理器自动包含（需注册新 context name）

#### 决策 2e：对记忆系统的影响

**→ 选择：压缩产物不进记忆文件体系（日志/笔记），仅进当轮 context**

**理由：**

- 记忆系统（`memory_log` / `MEMORY.md`）记录的是**跨会话持久化**的内容
- 对话历史压缩产物是**临时性上下文优化**，不应污染记忆文件
- 跨会话有价值的内容已通过 auto-memory 写入日志/记忆文件，无需额外处理
- 压缩摘要只在当前 session 内有效，跨 session 后自然失效

## 八、特别思考

### 8.1 "按需配给"与静态裁剪的边界

用户说"按需配给"，严格含义是工具**按需出现在上下文**。这与现有注入管理器的"静态固定裁剪"是不同维度：

- **静态裁剪**：哪些工具永远不在这个 preset 里（从 preset yaml 移除）
- **按需配给**：哪些工具默认不在，但任务需要时可激活

本计划采用**先静态后动态**策略：

- 静态：browser/vision 工具从 full preset 移除（省 token）
- 动态：注入管理器按 skill-router 分类结果动态 add 回来（按需激活）

这样既满足用户"按需配给"的意图，又保证静态基线已足够精简。

### 8.2 历史压缩产物与记忆系统的关系

用户之前定义了记忆文件规范（四类文件、六步处理管线）。压缩产物的定位：

- **不进记忆文件体系**：压缩摘要是临时性上下文优化，跨 session 无效
- **与 auto-memory 协同**：auto-memory 在每轮 turn-end 写日志（长期记忆）；压缩摘要写 context（短期上下文）。两者互补：
  - auto-memory → 跨会话知识固化
  - 压缩摘要 → 当轮上下文轻量化

### 8.3 廉价模型中转的用户约束

主 Agent 用 agnes-2.5-flash（免费），工具/历史设计要贴合省钱目标：

- 减少工具定义 token → 减少每轮输入 token → 直接省钱
- 减少历史上下文 token → 减少每轮输入 token → 直接省钱
- 压缩用免费模型（agnes-2.5-flash via router-9888）→ 压缩本身也省钱

预期收益：

- 静态裁剪后：单轮注入从 ~25.1K → ~19K（省 ~6K，约 24%）
- 每轮压缩后：10 轮对话后上下文不线性增长（平台期）
