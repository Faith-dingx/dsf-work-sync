## 二、上游更新获取通道方案

### 2.1 网络约束

- `api.github.com` 超时（本机 10.10.10.9 直连受限）

### 2.2 可选通道

| 通道                               | 可行性                      | 说明                                                                                     |
| ---------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------- |
| **A. `git fetch origin` 定时轮询** | ✅ 首选                     | 每 6h 或每日一次；慢但可靠；fetch 后 `git log HEAD..origin/master` 检测上游新 commit     |
| **B. GitHub 镜像站**               | ❌ **未验证，现阶段不可用** | 如 `ghproxy.com` 或校内镜像——2026-08-25 未实测通过，不能算可靠备选；若未来验证可用再升格 |

| **D. 手动触发**                    | ✅ 备用                     | 用户有更新意向时主动 fetch；适合不常更新的场景                                           |

### 2.3 推荐方案

**主通道 A + 备用 D**。具体：

- 每周或迁移完成后，执行一次 `git fetch origin && git log HEAD..origin/master --oneline` 核查（**注意方向：HEAD..origin/master = 上游有而本地无的 commit；反向 origin/master..HEAD 显示的是本地 33 个领先 commit，永远非空，禁止用**）

## 四、合并策略结论

### 4.1 推荐策略：**merge（非 rebase）**

| 策略         | 优点                                                                                                  | 缺点                                                                                                 | 适用性                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **merge** ✅ | 保留本地 33 commit 完整历史；冲突点清晰可追溯；**产出单一可逆 merge commit**；可回退到任意本地 commit | 历史树分叉，log 稍复杂                                                                               | **推荐**，符合当前"保留自定义历史"诉求                  |
| rebase       | 线性历史，更整洁                                                                                      | **重写本地 33 个 commit hash，破坏 `fork/backup/lan-access` 锚点与任何 tag/ref，且不可逆**；回退困难 | 不推荐。主因是 ref 稳定性（锚点失效），而非"失败更隐蔽" |

### 4.2 具体步骤（merge 流程）

> 注：merge 会在 `pre-merge-commit` 阶段触发 lefthook 钩子（lefthook.yml L44-54 有 `pre-merge-commit`：翻译配对 + 归档笔记校验）——若合并改动 `*.i18n.yaml` 会自动触发，属预期行为，通过即可。

```
1. git fetch origin                          # 拉取上游最新
2. git log HEAD..origin/master --oneline     # 确认有新 commit（当前输出为空）
3. git rev-parse HEAD > .temp/pre-merge-head.txt   # ★记录合并前本地 HEAD（回滚锚点，勿删；全程在 harness 目录执行）
4. 临时 worktree preflight：git merge --no-ff origin/master 演练冲突面（§3.2）；演练结束 `git worktree remove <临时目录> --force` 清理
5. git merge origin/master --no-ff           # 非快进 merge，保留 merge commit
6. 处理冲突（如有）→ 参考 §3.1 仲裁思路（lockfile 禁 --ours/--theirs）
7. pnpm install                              # 依赖更新（lockfile 重生成后核对 diff）
8. pnpm run typecheck + lint + test          # 门禁验证
9. pnpm run build:web                        # 构建 web 产物
10. 逐条核对 5 个本地插件加载日志出现 activated（防加载机制静默变更）
```

### 4.3 远程分支同步

- 合并完成后，`fork/feature/lan-access` 推送 merge commit（非 force）
- `fork/backup/lan-access` 保持原 HEAD 作为安全锚点（可随时 reset 回滚）

## 七、迁移软路由顺序建议

### 7.1 两种顺序

| 顺序                | 优点                                                                                | 缺点                                                                    |
| ------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **先迁移后更新** ✅ | 避免变量叠加；迁移时 harness 版本固定，后续更新只影响一台设备；本机出问题可随时切回 | 迁移后需再次验证（已在迁移清单中覆盖）                                  |
| 先更新后迁移        | 理论上只更新一次                                                                    | 迁移 + 更新两个变更叠加，出问题难定位；本机不稳定状态迁到软路由放大风险 |

### 7.2 推荐：**先迁移，后评估更新**

理由：

1. **自身稳定优先**：本机 33 commit 已充分测试，当前运行稳定；无必要主动打破
2. **避免变量叠加**：迁移涉及 6 个数据目录复制 + 新机器环境差异；更新涉及代码合并 + 可能的冲突；两件事分开处理，出问题好定位
3. **迁移即验证**：迁移后的验证矩阵（docs/dsh迁入软路由检查清单.md §四）已覆盖功能冒烟，相当于一次天然"更新后验证"
4. **远期目标**：所有设备统一指向 `10.10.10.2:9888`，迁移完成后多设备同时受益上游更新

### 7.3 具体顺序

```
1. 本机迁移：按 docs/dsh迁入软路由检查清单.md 逐项执行
2. 迁移后验证：确认软路由上 dsh 各项功能正常
3. 此时再评估：是否需要更新（检查 git fetch origin 是否有新 release）
4. 若上游有新 release：按本预案 §四~§六 执行更新
5. 若上游无新 release：维持现状，定期（每周）fetch 核查
```
