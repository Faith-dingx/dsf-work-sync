# 故障一根因防护方案（事务式对齐守卫）

> 2026-08-24 · 定案于主 agent 与用户多轮推演
> 对应故障：dsh-web 14:37 崩溃死循环（pnpm deploy --prod 污染 source workspace state → 自动 install --production → 删 411 devDeps → lefthook postinstall 崩 → 死循环）

## 一、根因复述（用户已确认）

| 层级 | 事实                                                                                                                | 证据                                                                  |
| ---- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 毒源 | `pnpm deploy --legacy --prod` 把 production mode 写进 source 的 `node_modules/.pnpm-workspace-state-v1.json`        | pnpm.mjs 195810 行 updateWorkspaceState(workspaceDir=source)          |
| 触发 | 14:37:08 用户手动 `systemctl --user restart dsh-web`                                                                | journalctl 无 agent 事件、config-ui 空闲                              |
| 机制 | pnpm 默认 `verify-deps-before-run=install`，读污染 state → 自动 `install --production`                              | pnpm.mjs 246829-246861 行 switch + 246869-246882 行 createInstallArgs |
| 崩溃 | 删 411 devDeps（含 lefthook）→ 根 postinstall `install-lefthook.mjs` ERR_MODULE_NOT_FOUND → exit 1 → systemd 死循环 | journalctl 14:37:11/18/25/33 四次循环                                 |

**关键洞察**：破坏性自动安装只在 pnpm 认为"对不上"时触发；若 node_modules 与 lockfile 永远全量对齐（dev 模式），自检是空操作。

## 二、设计原则（用户定案）

1. **唯一结局 = 全量对齐完成** —— "不能不启动"是硬约束
2. **动就要对齐，不留半尾** —— 依赖被触碰后，操作完成 = 全量对齐；未对齐则阻断操作者其他操作，直到对齐完成
3. **① 是主闸，②③ 是补漏** —— 主次顺序不可颠倒
4. **检测 + 提醒强制落地** —— 每次触碰依赖必须提醒，未对齐必须阻断 + 报警

## 三、三层设计

### ① 主闸：事务式对齐守卫（Host 级 Cordis 插件）

**定位**：防（不让毒源产生）+ 修（强制收敛）

**触发条件**：任何 agent（主 + 子代理）发起触碰依赖的操作，包括：

- pnpm 命令族：`install`、`deploy`、`add`、`remove`、`update`、`link`、`rebuild`、`dedupe`、`prune`
- 文件修改：`package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`.npmrc`
- 状态文件写入：`node_modules/.pnpm-workspace-state-v1.json`、`node_modules/.modules.yaml`

**生命周期**（每条依赖操作必须走完）：

```
操作发起
  │
  ├─ 提醒：告知"这是依赖操作，完成后将校验对齐状态"（agent 可见提示）
  │
  ├─ 操作执行（允许进行）
  │
  ├─ 检测对齐（自动，完成后立即执行）
  │     判据①：source workspace state settings.dev === true
  │     判据②：node_modules/.bin/lefthook 存在
  │     判据③：lockfile 与 package.json 一致（pnpm install --frozen-lockfile 验证）
  │
  ├─ 【通过】→ 事务提交，操作完成，不打扰
  │
  └─ 【未通过】→ 触发阻断流程：
         ① 报警："依赖未对齐，操作未完成"（journal CRIT + 标记文件 + 用户可见提示）
         ② 阻断：冻结该操作者（及其它想碰依赖的操作者）的其他操作
            —— 只放行一件事：CI=true pnpm install（唯一合法对齐动作）
         ③ 对齐完成后重新检测 → 通过 → 解除阻断
            —— 此刻原操作才算真正"完成"
```

**阻断语义**：

- 被阻断的 agent 后续所有工具调用一律拒绝（除 `CI=true pnpm install` 这一条），提示"依赖未对齐，先完成对齐才能继续"
- 阻断按 agent/session 粒度，不影响其它正常 agent
- 一旦对齐完成（检测通过），自动解除阻断，原操作的事务提交

**实现要点**：

- Host 层插件，监听 `tools/pre-execute`（与 guard-main-agent 同机制）
- 拦截范围：bash/shell 工具（匹配 pnpm 命令关键词）+ file write/edit 工具（匹配依赖相关文件路径）
- 对齐操作固定为 `CI=true pnpm install`（加性、确定性、全量、永不删 devDeps）
- 阻断状态存储在 host 层内存（不在磁盘，重启清零——符合"对齐失败 = 重启后重跑"语义）

### ② 补漏：启动收敛（dsh-web.service 改造）

**定位**：兜底，确保启动时永远是齐的

**改动**：

1. `dsh-web.service` 的 `ExecStartPre` 加一行：
   ```ini
   ExecStartPre=/bin/bash -c 'CI=true pnpm --dir /home/dingx/deepseek-harness install --no-frozen-lockfile'
   ```
2. `dsh-web.service` 的 `Environment` 加：
   ```ini
   Environment="pnpm_config_verify_deps_before_run=error"
   ```
   → pnpm 在 dsh-web 启动时发现对不上，只报错不自动装（拆掉自动对齐器，防"自动删依赖"）
3. `ExecStart` 保持 `pnpm dsh web` 不变

**效果**：

- 每次启动前强制全量对齐（加性，exit 0 才进入下一步）
- 启动时 pnpm 自检若发现对不上 → 报错退出，不自动装 → 不循环
- 对齐失败 = 启动失败（干净失败，日志暴露真实错误）

**"不能不启动"的保证**：

- 正常情况下：① 已保证启动时是对齐的 → 启动成功
- 污染时：② 启动前强制对齐 → 拉回 dev 模式 → 启动成功
- 极端情况（对齐真的失败）：见 ③

### ③ 补漏：免疫 + 报警

**定位**：最后一道防线，保证 dsh 永不因缺依赖崩启动

**改动**：`scripts/install-lefthook.mjs`

- 当前：`import('lefthook')` 硬崩溃（devDeps 被删就报 ERR_MODULE_NOT_FOUND）
- 改后：try/catch 包裹，缺失时优雅跳过并 **三级报警**：

```js
try {
  await import('lefthook');
  // 正常安装 lefthook
} catch (err) {
  // 报警 ①：journal/控制台 CRIT 警告
  console.error('[dsh-boot] CRIT: lefthook not found — production install detected');
  // 报警 ②：写标记文件
  const fs = require('fs');
  const alertDir = process.env.DSH_HOME || process.env.HOME + '/.dsh';
  const alertFile = alertDir + '/.alerts/production-install-detected.json';
  fs.mkdirSync(alertDir + '/.alerts', { recursive: true });
  fs.writeFileSync(
    alertFile,
    JSON.stringify({
      ts: new Date().toISOString(),
      reason: 'lefthook missing in postinstall',
      hint: 'A --production install was detected. Full align should restore. Check ① main gate logs.',
    }),
  );
  // 报警 ③：host 读取标记 → config-ui 红色横幅（待 host 插件实现）
  console.error('[dsh-boot] ALERT marker written to', alertFile);
  // 优雅跳过，不崩
}
```

**报警渠道**：

1. Journal/控制台 CRIT（`journalctl --user -u dsh-web` 可见）
2. 标记文件 `~/.dsh/.alerts/production-install-detected.json`（时间戳 + 细节）
3. config-ui 顶部红色横幅（持久，待用户确认才消失）—— 由 host 插件轮询标记文件实现

**"不能不启动"的结构保证**：

- ① 让启动时永远是对齐的（正常情况）
- ② 启动前再对齐一次（污染情况）
- ③ 极端情况下，即使对齐失败，postinstall 也不崩（只是没 git 钩子，运行不受影响）

## 四、边界与冲突分析

| 维度                         | 分析                                                                                   | 结论                                             |
| ---------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **与 guard-main-agent 冲突** | guard 基于 preset（仅主 agent），本守卫是 host 级（覆盖全部）                          | 不冲突，互补：guard 管文件权限，本守卫管依赖对齐 |
| **与 auto-memory 冲突**      | 本守卫在 host 层 pre-execute，不影响 auto-memory 注入                                  | 无冲突                                           |
| **与 config-ui 冲突**        | config-ui 是前端服务，不碰依赖                                                         | 无冲突                                           |
| **与 pnpm 流程冲突**         | `verify-deps-before-run=error` 只改 dsh-web.service 环境，不动全局 pnpm 配置           | 开发流程不受影响                                 |
| **重启后能否起来**           | ② 启动前必对齐，对齐成功才启动；极端情况 ③ 保证不崩                                    | 启动成功率 100%（结构保证）                      |
| **性能影响**                 | 每次依赖操作多一次检测（3 项轻量检查，< 1s）；启动多一次 `pnpm install`（~3s，已验证） | 可接受                                           |
| **阻断时 agent 体验**        | 被阻断的 agent 会看到 deny 提示（明确说"先完成对齐"）                                  | 可接受，且有提醒前置                             |

## 七、量化验收标准

| #   | 标准                                                         | 验证方式   |
| --- | ------------------------------------------------------------ | ---------- |
| 1   | 触发 `pnpm deploy --prod` → 守卫拦截或后置阻断 + 报警        | 人工测试   |
| 2   | 触发后 `CI=true pnpm install` → 解除阻断，事务通过           | 人工测试   |
| 3   | `systemctl --user restart dsh-web` → 启动成功（NRestarts=0） | journalctl |
| 4   | postinstall lefthook 缺失 → dsh 仍启动 + 报警触发            | 模拟测试   |
| 5   | 正常 pnpm install（无 --prod）→ 无报警、无阻断               | 人工测试   |
| 6   | 非依赖操作（如 `pnpm run build`）→ 不触发守卫                | 人工测试   |

## 八、风险与薄弱点

1. **阻断状态重启清零**：host 内存存储的阻断状态在 dsh 重启后丢失。若污染发生在重启前，重启后②会自动修复——可接受，但需文档说明
2. **第三方 pnpm 插件可能绕过守卫**：守卫只拦已知命令/文件，若有新工具写入 workspace state 则漏检。缓解：②③ 兜底
3. **`pnpm install` 本身可能失败**（网络/磁盘/仓库损坏）→ 启动失败。极端场景下 ③ 保证不崩但 ② 的 exit 0 门控会让启动失败。需在文档中标明"启动失败时检查 pnpm install 日志"
4. **config-ui 横幅需要单独实现**：③ 的第三级报警（config-ui 红横幅）需要 host 插件读标记文件并暴露 API，属独立小任务
