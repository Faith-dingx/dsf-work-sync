## 二、错配详述

### A. persona 文本与职责定位直接矛盾（文档层，影响最大）

`full/agent.cordis.yml` L23：_"You are granted FULL access … complete toolset … unrestricted permissions … Work autonomously and decisively: explore, implement, test, and verify."_

与《主agent职责边界.md》§一"**主 agent 是编排者，不是实施者**——只做规划、派发、汇总、决策、兜底，不亲自写代码、不独立跑验证"直接冲突。实际防护只靠机制层（guard 白名单拦截 edit/write/bash 越界 + rm 硬禁），persona 文本牵引力仍是"大胆实施"。历史跑偏事件（2026-08-24 规划师绕 read-only 越界改代码）同源。

- 证据：本会话连续 2 次 edit preset 文件即被 guard 拦截并自动转派（10:31/10:34）——机制兜底生效，但说明主 agent 在 persona 引导下持续尝试实施动作。
- 影响：每次拦截 = 一次 token 往返 + 转派开销；更危险的是 persona 不引导"先派发"，全靠失败后纠正。

**建议**：给主 agent persona 追加"编排者"定位段落（引用职责边界文档 §一/§三禁止项/§六熔断），替换或弱化 "implement, test, and verify" 的自主实施表述；明确"preset/配置/代码类文件修改一律转派 code-agent，主 agent 不得自行 edit"。

### B. tool-cordis 动态插件 = 绕过 guard 白名单的 JS 执行通道（机制层，最严重）

`full/agent.cordis.yml` L370-371 挂载 `tool-cordis`（cordis_define/run 等），preset 头部注释自述 _"Treat a session on this preset as shell access"_（L11）。

- cordis_define 的 host code 是**任意 JS 函数体**，在 dsh 宿主进程内 apply 执行，可触及真实 Service（文件、网络、命令、会话、agent 注册）。
- guard-main-agent 只拦 shell 工具与 edit/write 的文件路径，**拦不住 cordis 插件内部 JS 写文件/执行命令**——这是主 agent 目前唯一的机制层越权通道，与"编排者"定位严重不符。
- 原厂设计理由（自省 agent 可授意 author 另一个 agent）与职责边界冲突；主 agent 无需动态插件能力（四个固化子代理 + plan-reviewer/check-agent 已覆盖全部实施面）。

**建议**（择一）：

1. 断然方案：full preset 移除 `tool-cordis` 行（或 cordis_define/run 类工具 disabled），仅保留只读 inspect 能力——实施/自省面全部归子代理；或
2. 保守方案：维持现状但 persona 明令"cordis 工具仅限本轮任务明确需要时使用，禁止用于写文件/执行命令"，并接受机制层无法强制。

### C. 固化子代理模型表：配置与职责文档 v1.2 不一致（文档过期）

| 角色          | 职责文档 v1.2（08-23）  | full preset 实际（08-25）                   |
| ------------- | ----------------------- | ------------------------------------------- |
| plan-reviewer | agnes / agnes-2.5-flash | **opencode-go / hy3**（L243-245）           |
| code2-agent   | **未收录**              | huoshan / deepseek-v4-pro（新增，L219-221） |
| 其余四角      | 一致 ✅                 | 一致                                        |

- plan-reviewer 换 hy3 与文档不符（可能是有意升级——hy3 比 agnes-2.5-flash 强，评审质量更高但付费）；职责文档应同步或回退。
- code2-agent（同 code-agent 职责、更强模型"复杂收尾任务用"）是既定角色，职责边界文档五环表未收录，应补 §2.1 或在五环表加一行。

**建议**：更新《主agent职责边界.md》五环表：plan-reviewer 模型改 opencode-go/hy3、新增 code2-agent 行（huoshan/deepseek-v4-pro，P2 复杂收尾）。

### D. bash 简单诊断路径在分类器故障时被 guard fails-close 掐断（运行时错配）

guard-main-agent `fallback: 'close'`（L272）：分类器（http://10.10.10.2:9888）不可达时 bash 全部 fails close。本会话 10:38-10:47 连续 3 次 `bash` 被吞（"classifier unavailable; code-class tool fails close"）自动转派 code-agent。

- 职责表安排"简单诊断 = 零闸自主"，但分类器一抖主 agent 连 `git status`/`curl` 只读命令都跑不了，被迫转派（每次都多一次子代理开销）。
- guard 对只读命令（git status/curl GET/ls/ps 等）无 fail-open 白名单。

**建议**：guard 增加"只读命令 fail-open"分支（与 rm 硬禁对称：rm 无条件 close，只读探测无条件 open；写操作 close），或分类器不可用时降级到本地规则判定。

## 三、总体判断

工具**不缺**（编排五件套齐全、校验类已补齐），问题是**过度授权 + 文档滞后**：

1. 优先处理 B（cordis JS 通道）与 A（persona 矛盾）——一个机制层、一个文档层，修复后主 agent 的"实施能力"与"编排职责"才真正一致；
2. C 是文档同步小事（10 分钟）；
3. D 是可用性体验问题，视软路由 9888 稳定性定优先级。
