## 一、故障一背景速览

2026-08-24 14:37 的崩溃循环根因链：

1. `pnpm deploy --legacy --prod`（软路由打包脚本）把 **workspace state**
   （`settings.dev: false / production: true`）写进了 source 的
   `node_modules/.pnpm-workspace-state-v1.json`；
2. 用户 `systemctl restart dsh-web` → 启动时 pnpm 自动 deps-status-check 读到
   污染 state → 自动 `install --production` → 删光 411 个 devDeps（含 lefthook）；
3. 根 `postinstall` ERR_MODULE_NOT_FOUND → 死循环。

本次实施的 `dsh-dep-align-guard` 是**防止复发的主闸**：任何触碰依赖的操作
完成后必须证明"对齐状态"成立，否则按 agent 粒度阻断，直到执行唯一修复命令
`CI=true pnpm install`。

## 三、核心逻辑

### 3.1 触发条件（tools/pre-execute 检测）

**pnpm 命令**：`bash` / `terminal_send` 的 `command` / `text` 字段中出现
`pnpm` 后跟依赖操作子命令：

```
install | deploy | add | remove | update | link | rebuild | dedupe | prune
```

解析器（`detectPnpmOperation(s)`）逐词扫描：跳过旗标（含带值的
`-F/--filter/-C/--dir/--cwd/--config/--reporter` 与 `--opt=val` 单 token），
第一个非旗标词即子命令；`run/exec/dlx/x` 前缀按脚本调用豁免；
`&& ; | || (` 视为命令链分隔符，终结该 pnpm 段。支持 `corepack pnpm` 前缀。

**受管清单文件修改**：`write`/`edit` 的 `file_path`、`str_replace_editor` 的
`path` 命中以下任意路径（任意层级后缀匹配）：

```
package.json | pnpm-lock.yaml | pnpm-workspace.yaml | .npmrc
node_modules/.pnpm-workspace-state-v1.json | node_modules/.modules.yaml
```

### 3.2 提醒前置（不阻断）

pre-execute 命中依赖操作 → logger 警告
「依赖操作 X（agent=Y）：完成后将校验对齐状态」→ `next()` 放行。
（PreToolDecision 无 warn 类型，提醒走日志 + post-execute 的上下文消息；
详见"设计取舍"。）

### 3.3 对齐检测（tools/post-execute，操作完成后）

对命中依赖操作的工具调用，post-execute 执行 `runAlignmentCheck`：

| 判据 | 检查                                                                    | 结论                              |
| ---- | ----------------------------------------------------------------------- | --------------------------------- |
| ①    | `node_modules/.pnpm-workspace-state-v1.json` 的 `settings.dev === true` | dev / nondev / missing            |
| ②    | `node_modules/.bin/lefthook` 存在（跟随符号链接）                       | present / missing                 |
| ③    | `pnpm install --frozen-lockfile --dry-run`（`CI=true` 环境）            | ok / mismatch / unknown / skipped |

- **对齐 = ①dev + ②present + ③≠mismatch**。
- **全新安装豁免**：`node_modules` 整体不存在（或不是目录）时视为"未触发"，
  不阻断——避免把仓库第一次 `pnpm install` 误杀。
- **fail-open 决策（判据③）**：dry-run 退出码非 0 且 stderr 含 lockfile 特征
  （`outdated lockfile` / `ERR_PNPM_OUTDATED_LOCKFILE` / `lockfile is not up to date`
  等）→ mismatch = 未对齐；其余错误（spawn 失败 / 命令不存在 / 超时 / 网络）→
  unknown，**不据此阻断**（①② 仍是硬判据）。判据③ 可用配置
  `runLockfileCheck: false` 关闭（重型仓库），此时记 skipped。

### 3.4 未对齐处置

1. **报警**：写 `~/.dsh/.alerts/dep-misaligned.json`
   （`{ updatedAt, incidents: [...] }`，每 incident 含时间戳、agent、工具、
   操作、workspaceRoot、三判据观察、细节；chmod 600）。
   只在 aligned→blocked **转换**时写一次，避免处于阻断态时重复刷盘。
2. **阻断（按 agent 粒度）**：`blockedByAgent: Map<agentKey, BlockState>`
   只存在 host 内存，**重启清零**。已阻断 agent 的后续任何工具调用
   （包括 read/grep 等只读工具）一律返回
   `{ kind: 'deny', reason: '依赖未对齐，请先运行 CI=true pnpm install（阻断时间 …）' }`。
3. **只放行对齐命令**：`isAlignmentCommand` 判定整条命令里出现的所有 pnpm
   依赖操作必须**全部是 install** 且带 `CI=true`（允许 `--no-frozen-lockfile`
   `--force` 等旗标）；`CI=true pnpm install && CI=true pnpm deploy` 这类混入
   其它操作的命令**不算**对齐命令。
4. **自动解除**：对齐命令完成后 post-execute 复查；对齐恢复 → 解除阻断 +
   上下文提示"对齐校验通过"。

### 3.5 上下文消息

post-execute 用 `createUserMessage`（`@deepseek-ai/dsh-llm`）把对齐结果附加为
`additionalContexts`，随下一次模型请求送达 agent：通过时
「依赖操作 X 已完成，对齐校验通过（dev/lefthook/lockfile 观察值）」；
未通过时给出判据明细和修复命令。下游已返回非 accept 决策时原样透传；
下游 accept 自带上下文时合并追加。

## 四、设计取舍与 API 现实

- **PreToolDecision 无 warn 类型**：任务书中"返回 `{ kind: 'warn' }` 提示再放行"
  在 `@deepseek-ai/dsh-tools` 的决策类型（`allow | deny | ask`）中不存在。
  落地为：pre-execute 返回 `next()`（放行）+ logger 警告，提醒正文通过
  post-execute 的 `additionalContexts` 送达 agent。已在代码注释和本报告说明。
- **阻断范围**：spec 要求"后续工具调用一律拒绝（除对齐命令）"，包括只读工具；
  因为 node_modules 状态是 host 级共享的，被污染后任何 agent 的操作都不可信。
  粒度按需求实现为 per-agent（未带 agent 时回退到根调用号）。
- **告警路径不做 fail-close**：告警文件写入失败只记日志、不阻断——证据缺失
  不能成为二次伤害。

## 七、cordis/host.js（动态宿主半场）

纯 JS、零 import，逐字对齐静态包的检测/阻断/恢复逻辑，供 cordis_define
沙箱使用。沙箱限制（无 require/process/Buffer/fetch/timers）下的取舍：

- 文件访问走 `ctx.fs`（`@deepseek-ai/dsh-fs` 服务：resolve/stat/readText/
  writeText），特征检测后使用；宿主未提供 fs 服务或未配置 workspaceRoot 时
  **降级为只提醒不校验（fail-open + 大声记录）**——不能验证的半场绝不砸系统；
- 判据③ dry-run 需要 subprocess，沙箱不可用 → 固定 `skipped`（静态包执行）；
- 家目录/环境变量不可解析 → `alertDir` 需显式配置，否则仅日志。

## 八、风险点

1. **阻塞激进性**：阻断期连只读工具也拒绝，可能影响正在排障的 agent；
   缓解 = 阻断状态重启即清零 + 明确修复命令 + 上下文里给出明细。
2. **判据③耗时**：每次依赖操作后跑一次 frozen-lockfile dry-run（秒级），
   高频依赖操作场景有延迟；重型仓库可 `runLockfileCheck: false`（①② 仍生效）。
3. **检测精度**：命令/文件识别基于词法与文件名，极少数误报（如脚本内
   `pnpm install` 字样、`docs/package.json`）只会触发"检查→通过"，不会阻断；
   漏报风险集中在 `deploy` 等污染命令的非常规写法（如别名包装），
   判据③/① 的磁盘事实检查仍能兜底。
4. **多实例**：阻断表是单进程内存；若 host 有多个 worker 进程，各进程独立
   判定（重启清零语义一致）。
5. **host.js 半场能力弱**：沙箱无法跑 dry-run 且依赖 ctx.fs；作为正式防线
   必须挂静态包 `lib/index.js`，host.js 仅作动态演示/兜底。
6. **告警目录权限**：`~/.dsh/.alerts` 首次写入需可创建（mkdir recursive +
   chmod 600）；失败不阻断。
